# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Purpose

Python tooling that works with data from [Project Sidewalk](https://github.com/ProjectSidewalk/SidewalkWebpage) to (1) download Google Street View / Mapillary panoramas and their GSV depth maps, (2) crop sidewalk-accessibility labels out of those panoramas for ML/CV use, and (3) monitor the nightly scrape across all cities. `DownloadRunner.py` is actively maintained; `CropRunner.py` still works but is being replaced (bugs may linger).

## Common Commands

Everything runs from a virtualenv — **there is no Docker in this repo**. The image and its sshfs entrypoint were retired from the repo in Aug 2026 and from the production box on 2026-09-01 (`docs/history.md`); production is **one** crontab line running `scrape_queue.py` (#101) from `.venv/bin/python`, with the pano store mounted on the host — `docs/ops.md`, Operating the production host.

```bash

PS_SFTP_HOST=... PS_SFTP_BASE=... python3 DownloadRunner.py <fqdn> <storage-dir> --from-store <city_id> [--with-depth]

# Nightly queue (the whole fleet, one cron line). --dry-run prints the plan and takes no lock. Refuses (exit 5) a
# --store-root without its .pano-store marker (#161; docs/ops.md, "The store marker").
python3 scrape_queue.py --cities <manifest.csv> --store-root <dir> \
    [--max-runtime MINUTES] [--city-max-runtime MINUTES] [--only CITY_ID] [--no-rotate] [--single-pass] [--dry-run] \
    -- [DownloadRunner args...]

# The alarm channel (#141): cron's mail-on-output rule for a host with no MTA. Runs COMMAND, streams its output
# through, and hands the capture to --sink (production: `aws sns publish ...`) when there is any. Exit code is
# COMMAND's; 4 = COMMAND exited 0 and the sink failed; 127 = COMMAND could not start (reported through the sink).
python3 cron_notify.py --sink '<shell command>' [--name NAME] [--only-on-failure] [--max-bytes N] [--log FILE] -- COMMAND...

# Cropper (exits 1 if any label errored; missing/untrusted panos alone are not an error). --force re-cuts existing
# crops (#83); a -o that looks like the production canvas-capture crop store, or that crop_rule.json records as
# another city's, is refused: exit 3, nothing written. --city is required (label_id restarts per city; #159)
# and must be an active row of log_analyzer/cities.csv (exit 2 otherwise). --sizing-rule v3 is opt-in (#32).
python3 CropRunner.py (-d <fqdn> | -f <metadata.csv|.json>) -s <pano-dir> -o <crop-dir> --city <city_id> [--mark-label] [--force] [--sizing-rule {v2,v3}]

# One-off migrator for pre-v2 depth artifacts
python3 migrate_depth_artifacts.py <storage-dir> [--dry-run]

# One-off, move-only migrator for a pre-#159 flat crop store into <crop-dir>/<city>/ (#159). Never replaces a
# file: a collision is listed and both are left. Exits 0 done / 1 anything left in place / 2 usage / 3 refused.
python3 migrate_crop_store.py <crop-dir> --city <city_id> [--dry-run]

# The display copy beside every wide pano (#115); idempotent, resumable. Neither downloader writes one any
# more (switched off 2026-09-09) - this is the only writer that CREATES one, and it runs only when you run

python3 downscale_panos.py <storage-dir> [--dry-run] [--max-runtime MINUTES] [--max-width PX] [--min-width PX]
```

**Coverage** is configured in `.coveragerc` (#57) and gated by its `fail_under`. Three things about it are load-bearing and easy to break by "simplifying":

- **The measured set is the production tree only** — every top-level/`downloaders/`/`log_analyzer/` module (a count is not written here: it has been stale twice). `reports/*` and `flag_panos/*` are omitted, the first because averaging a large body of frozen study tooling in would let the scraper's number move several points unnoticed, the second because its module scope writes files at import. `tests/test_coverage_config.py` asserts the resolved set exactly, so adding a module is a deliberate measure-or-omit decision.
- **`source` is written as `${SIDEWALK_COVERAGE_ROOT-.}`, not `.`** — coverage resolves a relative source against each *process's* CWD, and the runner tests spawn subprocesses with `cwd=tmp_path`. `tests/conftest.py`'s `pytest_configure` sets that variable (plus `COVERAGE_PROCESS_START` and `COVERAGE_FILE`) only when the parent is itself being measured. Break any of the three and `main()`, the argparse `type=` validators and the budget carve-out all read as dead: `DownloadRunner.py` drops from 97.6% to 87.9% with nothing failing. Every `omit` pattern is anchored to the same root (`${SIDEWALK_COVERAGE_ROOT-.}/tests/*`, ...) for the same reason, and `test_coverage_config.py` asserts it: a relative omit is anchored to the child's CWD too, so a child that loads `tests/conftest.py` from `tmp_path` put it in the measured set and took CI from 99.46% to 98.07% with nothing failing (#171 review). The same hook, unconditionally and *before* that early-returning coverage block, points the children's `TMPDIR`/`TEMP`/`TMP` at a per-session dir (#165), so they never touch the host's real pacing lock, block latch, width-alarm latch or queue lock. Keep it above the `return`: in an ordinary measured run that `return` never fires (the hook sets `COVERAGE_PROCESS_START` itself, below it), but a session started with the variable already exported, or with no `coverage` installed, does return early, and would then skip the redirect.
- **`branch = True`** — the gap that motivated the gate was an `if` that only ever went one way (three of the log analyzer's six alert rules never fired while every line around them was green; that was the count at the time of the #57 measurement, and rule 4's `median > 0` guard turned out to be a fourth such `if` — see the log_analyzer notes below).

## Architecture

`DownloadRunner.py` (#52) and `CropRunner.py` (#48) both follow the same extracted #52.1 shape: `build_parser()` / `configure_logging()` / `run(...)` / `main(argv=None)` behind an `if __name__ == '__main__'` guard, so **importing either has no side effects** and tests can drive the real flow in-process. (`tests/test_log_analyzer.py` still lifts `LOG_CSV_FIELD_COUNT` out of `DownloadRunner.py` with `ast`, but that is now just avoiding the import cost, not a workaround for a module-scope `parse_args`.) Per-source download logic lives in the `downloaders/` package, which is also safe to import.

**DownloadRunner.py** — orchestrates a nightly run: fetch the pano list, download images, download depth, write one `log.csv` row.
1. Fetches the pano list from `/adminapi/panos` (or a CSV via `-c`), using a `requests` session with retries and explicit timeouts. Drops empty ids and `'tutorial'`. `filter_supported_sources()` keeps `gsv` and `panoramax` unconditionally, plus `mapillary` when `MAPILLARY_ACCESS_TOKEN` is set; filtered-out panos are deliberately **not** written to `pano_id_log.csv` so a later run can still pick them up — and are reported as the run conditions `mapillary-token-missing` / `unsupported-source` (#161), because a skip that is never ledgered is also never seen. Three more runner conditions sit around the phases: `pano-list-empty` (an empty list as served, before the source filter, for a store whose ledgers have a row past the header — `_store_has_history`, so a fresh store stays quiet), `images-no-success` (none of this run's attempts was answered and either at least `IMAGE_NO_SUCCESS_MIN_RAISED` = 10 raised or the phase stopped on `max-runtime` with at least one raise whose mean duration is at least `IMAGE_NO_SUCCESS_MIN_MEAN_RAISE_SECONDS` = 60 s, the dropped-packet outage where each raise takes ~3.5 min — without that gate a mature city's few slow perennial raisers filling the image share alarmed nightly, and the detail carries `S s per raise` on both arms for the floor measurement; the budget arm is keyed on `image_stop == 'max-runtime'`, so it never fires on #172's push-back trip (`image_stop='blocked'`) — but the **count arm can**: a transient does not reset the push-back count, so enough network raises between refusals reach the minimum before the trip and both are reported, kept deliberately because those raises were real and the city is booked failed either way; skips count as neither, a permanent verdict is an answer, so is a `FrameDisagreementError` (#74: unledgered, but Google answered — an answer, so one blocks the condition), a GSV push-back (#162) is a raise, the gate is the **mean** raise duration, never the slowest, and the counters are per run, never the ledger-seeded `fail_count`), and **`pano-schema-drift`**, the one condition that also stops work: when `INTAKE_SCHEMA_MIN_FRACTION` (0.9) or more of the records as served lack a key in `INTAKE_REQUIRED_KEYS` (`pano_id`, `source`, `width`, `height` — a missing **key**, never a blank value, counted per record; `/adminapi/panos` writes a null dim by omitting the key, so there only the fraction tells a dimensionless pano from a rename), neither phase runs, nothing is ledgered, and the `log.csv` row is written with every phase blank. The alternative is irreversible: a renamed `width` makes `resolve_zoom_and_dims` return `None` and every new GSV pano a permanent `downloaded=0`, fleet-wide in one night, with no GSV breaker by design (#113). The guard reads the list before `filter_supported_sources`, so a renamed `source` is drift rather than N unsupported-source lines. `RUN_CONDITIONS` is the whole vocabulary.
2. `select_image_panos()` applies `--all-panos`. **This gates images only** — the depth phase always gets the full corpus, since depth is wanted for unlabelled panos too and costs the same either way.
3. Runs the image phase, then the depth phase, then appends one `log.csv` row in a `finally`. Both phases share `--max-runtime`; `--min-depth-runtime` carves a reservation out of the image phase's share so an image backlog can't starve the depth backfill (only taken when `count_unresolved_depth()` shows work pending).
4. Budgets use `time.monotonic()`, never the wall clock, so an NTP step or DST transition can't stretch or shrink them.
5. `--run-summary-file` writes `{image_stop, depth_stop, conditions}` — what stopped each phase, plus the run's **conditions** (#161): `{code, detail}` for each shape the runner calls a failure of the night without changing its exit code, recorded through `downloaders.common.note_condition` (one entry per code, first detail wins, detail capped at `CONDITION_DETAIL_MAX`). `_write_run_summary` always writes the `conditions` key, `[]` on a clean run. The stop reasons are seeded to `None` so "finished its list" is distinguishable from "never ran". It is the channel `scrape_queue` reads — its extra passes (#43) and the night's exit code (#161) — and nothing else reads it; no flag means no file. Written in a `finally`, so a crash in the pano-list fetch still reports, and a failure to write it is a warning, not a fatal. `tripped_sources` carries #113's trips and the GSV push-back trip alike (#162), and a push-back trip records `image_stop: blocked`. Both phases record through an out-parameter dict for the same reason `tripped_sources` is one: their return tuples **are** `log.csv` columns and must not be widened. `SIGTERM` is translated into `sys.exit(143)` so a stop (`systemctl stop`, a cron timeout wrapper, an operator's kill) runs `finally` blocks instead of discarding the evidence row. Logging goes to `scrape.log` **on the pano store**, not the CWD — under cron the CWD is wherever the process happened to start, which is nowhere anyone looks.
6. **Store mode (`--from-store CITY_ID`, #30) is a *phase*, not a *source*.** `pull_panos_from_store` sits beside `download_panorama_images` and returns the same `log.csv` 7–11 tuple (column 8 a constant 0); the transport is `downloaders/store_sftp.py`. One `sftp -b -` session per `BATCH_SIZE` (100) ids, opening with an **unprefixed** `cd` into the city folder (the probe: a wrong city id fails the session on line 1 instead of reading as 100% absent) and then one **`-`-prefixed** `get` per pano (so one absent pano cannot abort the other 99). Every path is double-quoted; each remote one is `./<id[:2]>/<id>` **relative to the probed directory** (a relative `PS_SFTP_BASE` repeated after the `cd` made every pano absent with exit 0, and the `./` keeps an id beginning with `-` away from `get`'s option parser) and each local one is absolute. Per-pano verdicts are decided from the local filesystem after the session — SOF plus an EOI that closes the image for a JPEG, a complete zip for a `.npz` — and placed through `atomic_output_path`; a read error while verifying is `truncated`, and only a failed rename is `unplaced` (local storage), which gets its own closing line on both channels saying a retry will not fix it (check local disk and the mount), where every other unledgered outcome says "retried next run". **It never writes a permanent verdict**: only `1` rows (blank `fetched_at`); absent, truncated and unplaced panos are counted in field 9 and unledgered, because the store is a moving target. A failed *session* stops the phase and adds `store_sftp.STORE_SOURCE_NAME` to the tripped set, so `main()` exits 1. Depth is skipped (Google is never contacted) unless `--with-depth`, which pulls stored artifacts and never touches `depth_log.csv` — `gsv.download_depth_maps` self-heals the ledger later at zero requests. `filter_supported_sources(require_credentials=False)` keeps Mapillary panos without a token. The connection settings are the log analyzer's `PS_SFTP_*` variables (or `--sftp-*` flags), resolved in `main()` before the storage dir or `scrape.log` exists; `sftp` runs with `BatchMode=yes` and `StrictHostKeyChecking=accept-new`, and its stderr is redacted and capped before it reaches either channel — the configured host/user/key, the configured port as a whole word, what `ssh -G <host>` resolves an alias to (whole words only: it always reports *some* user and port, on a plain host the local login and 22), and patterns for `port N`, `]:N`, IP literals and `name@`. `tests/conftest.py` points `SSH_CONFIG_COMMAND` at a missing binary so the suite never reads a real `~/.ssh/config`. The image ledger's open/header/append code is shared as `ImageLedger`.

**downloaders/** — per-source download logic; `download_pano()` dispatches on `pano_info['source']`.
- `gsv.py` stitches 512×512 tiles from Google's undocumented `cbk?output=tile` endpoint into one equirectangular JPEG. **The zoom comes from photometa's own `image_sizes` (#74)**: `resolve_frame(pano_info)` → `ResolvedFrame(width, height, zoom, consistent, served_dims, evidence, refusal)` makes one `download_depth=False` photometa request (16 KB) and `choose_zoom` picks the highest level `k` whose `_dims_at_zoom(app_w, app_h, k)` IS the reported level — a consistency check, not "the top level". It reproduces the probe's answer for every six-level shape, picks the native top level for the four- and five-level ones (the probe could only say 5 or 3, so a five-level 5376×2688 pano moves from `log.csv` field 8 to field 7), and fetches a lower matching level natively where the probe fetched its top-left corner. A frame no level admits (`refusal='frame'`) or non-512 tiles (`'tile_size'`) comes back `consistent=False`, and `download_single_pano` refuses it with `FrameDisagreementError` — a stdout print plus the one `ERROR` the runner logs with the exception text, both containing `frame disagreement`; raised, so it is a counted, unledgered, retried-next-run failure. The old two-tile probe survives verbatim as `_probe_zoom`, the fallback for **every** photometa failure (deliberately broad) and for photometa's code 2, so a permanent `downloaded=0` still rests on the two black tiles (plan decision D5: GSV has no breaker) — **on a 200**: `_get_response` raises, closing the response first, on any other status, so a 403/404 black body is a retry, never a ledgered verdict, and never lets `frame_covers_pano` pass a frame (#166). **The probe cannot tell a frame from a crop, so on that arm `download_single_pano` runs `frame_covers_pano` before the fan-out** (two more requests, only on fallback panos) and refuses the same way — without it every photometa failure or latched night stitched and ledgered the crop a photometa refusal holds off. **That check guards a frame SMALLER than served, not one LARGER**: 16384 on a pano served at 13312 has nothing past its grid, stitches ~34% black (under the 0.5 limit) and is ledgered; the photometa arm refuses it, the probe arm does not (pre-#74 residual, not fixed by it). Photometa's health is remembered per run (`_PhotometaRunMemory`, reset by `DownloadRunner.run`, which also sets the image phase's latch and pace paths): three non-refusal failures in a row, or one refusal (the latch write never raises, so the file cannot be relied on), and the run stops asking; the first failure, refusal or fresh latch of a run is announced once on both channels (a "not found" is not). The tiles are then fanned out concurrently via `aiohttp` with `backoff` retries, pasted into a blank canvas sized per the app's width/height, and upscaled with LANCZOS when only a lower level exists.
  - **The imagery and the verdict are two seams (#73).** `resolve_zoom_and_dims(pano_info)` → `(w, h, zoom)` or `None`, and `fetch_pano_image(pano_id, w, h, zoom)` → `StitchedPano(image, undersized_tiles, upscaled)`; `download_single_pano` is their composition plus the exists check and the atomic save. Since #74 `download_single_pano` composes `resolve_frame` (and applies the frame-disagreement refusal), while `resolve_zoom_and_dims` is `resolve_frame(..., photometa=False)`: **the probe alone, no photometa request, no latch read or write**, so `refetch_panos.py` keeps its pre-#74 decisions. Through photometa, two of its refusals became swaps (a stored 8192×4096 on a 16384 pano: `frame_grew` → `replaced`; a five-level 5376×2688: `upscaled` → `replaced`) — possibly better imagery, but changing what the repair pass does is its own decision, and `TestRefetchKeepsItsPre74Decisions` pins both through the real seams. `refetch_panos.py` composes the same two with different gates, so a repair pass cannot become a second stitcher — which is the #73 failure mode one level up, and would be just as invisible, since both would still produce a plausible JPEG at the reported dims.
  - **`fallback_success` is "the stitch was upscaled", not "zoom == 3".** `download_single_pano` returns it when `_dims_at_zoom(w, h, zoom) != final_im_dimension`, which is exactly when `_stitch_tiles` had to LANCZOS the frame up to the reported dims. Those two rules disagree on the panos that matter: an old four-level pano (3328×1664) has max zoom 3, so zoom 3 *is* its native resolution and nothing was lost. Two tests hold that split apart and both kill a `zoom == 3` implementation. Nothing returned this verdict at all until #52, so `log.csv` column 8 was a constant `0` for every run before it — and `log_analyzer` sums that column into `daily_success`, so it was adding a permanent zero.
  - **A tile refusal is push-back, not a transient (#162).** `_fetch_tile` turns HTTP 429/403, or a landing URL (or redirect hop) carrying `_BLOCK_URL_MARKERS` **at any status** — the session raises for a non-2xx landing before the in-context check sees it, so the except arm checks `request_info.real_url` and `history` too — into `TilePushbackError`, which is deliberately **not** an `aiohttp.ClientError`, so the backoff decorator never retries it; `_tile_error_is_final` stops any other 4xx but 408 from being retried (a 404 is this pano's problem, not weather); 5xx/408/network/wrong Content-Type keep `TILE_MAX_TRIES` tries, each wait capped at `TILE_RETRY_MAX_WAIT`, and no retry once the tile has spent `TILE_RETRY_MAX_SECONDS` of **its own time** — since its first attempt began, **less every wait for a fan-out slot, the first and each retry's** (both limits read at call time, so tests can zero them). That budget is in the giveup predicate (`_tile_retry_budget_spent`, reading a per-task `_TileClock` context variable that `_fetch_tile` adds each slot wait to), **not backoff's `max_time`**, whose clock starts with the task: all 512 tasks start at t=0 and queue for a slot, so `max_time` let the queue spend the late tiles' retries on exactly the slow nights they matter. Excluding only the first wait is not enough: a retry re-queues behind every tile not yet started, so the tiles that failed *first* lost their retries instead (~128 s of re-queue at 512 tiles, 8 slots and 2 s a tile). `test_time_queued_for_a_slot_does_not_spend_a_tiles_retry_budget` pins both, failing the last tile and the first. Before this, a refused 16384-wide pano cost 5,120 requests. The decorator runs with `logger=None`: backoff logged 512 × 9 INFO + 512 ERROR lines per failed pano, so capping its logger at WARNING would still have left 512 ERROR lines — don't "fix" the flood that way.
  - **One refusal abandons the pano; one line per pano.** `fetch_pano_image` sets `_TILE_FANOUT` (a `_TileFanOut`: slot, requests, retries, refused) around `asyncio.run`; `_fetch_tile` takes the slot, *then* checks `refused` (all 512 tasks start at t=0, so a check before the slot sees nothing), so a refused 512-tile pano costs `thread_count` requests, not 5,120. It is a **context variable, not a parameter**, because `_download_tiles(tiles)` and `_download_tile(session, tile)` are stubbed by exactly those signatures across the suite; unset (direct calls), behaviour is pre-#162. Only a refusal abandons — an ordinary failed tile still lets the rest finish (#45's contract, `TestTheTileFanOutContract`). A refused pano is raised **without** a log line (the image loop writes it, `(HTTP N)`); an ordinary failure keeps its one ERROR, now with the retry count; a success that needed retries gets one INFO.
- `gsv.py` also owns the **depth phase** (`download_depth_maps`), which fetches depth via the `streetlevel` library's photometa call — one metadata request per unresolved pano.
- `mapillary.py` resolves `thumb_original_url` via the Graph API and downloads it. Requires `MAPILLARY_ACCESS_TOKEN`.
  - **Its permanent verdict rests on positive evidence (#99).** The metadata request asks for `id,thumb_original_url`, and `original_rendition_url()` returns the no-rendition verdict only when the body names the image and lacks the URL. A 200 carrying an `{"error": {...}}` envelope, a non-object body, or a record naming a different image raises `MapillaryErrorResponse` instead, so it counts among tonight's failures and ledgers nothing. Every auth failure measured 2026-09-05 was a non-200 wearing that envelope (pinned as data in `tests/test_image_downloaders.py`), so the check covers the one shape nobody can measure without a live token; the composition through the real dispatcher into `pano_id_log.csv` is pinned in `tests/test_download_runner.py`. A 404 is read too, but only for the measured auth signature (`is_auth_envelope`: code 190 or type `OAuthException`), because a Meta-style 404 for a retired image carries an envelope as well, and refusing any envelope there would re-request every retired image nightly forever. The image body is checked with `jpeg_dimensions` before the rename, since a saved `.jpg` is the resume marker and an HTML error page from the CDN would be permanent with no ledger row to edit. Measured 2026-09-06: Mapillary's "does not exist" is a **400** with code 100 / subcode 33, not a 404, and it raises unledgered by decision, since its message conflates "does not exist" with "missing permissions" and a scope-less token would produce it for every pano. The breaker that would bound that damage now exists (#113), but it does not make the body less ambiguous, so writing 100/33 off stays a separate decision on separate evidence. The cost is one request per retired image per night. **That measurement leaves the no-rendition verdict as the only permanent path production reaches**, and a scope-less token need not send an envelope at all — Meta's Graph family answers a permission-denied field by omitting it from an otherwise healthy 200 record, which is that exact shape. `DownloadRunner.MAX_CONSECUTIVE_PERMANENT_FAILURES` is the breaker that closes it (#113).
- `panoramax.py` (#110) resolves `GET /api/pictures/<uuid>` at the keyless meta-catalog `api.panoramax.xyz` and follows the item's `assets.hd` href to whichever federated instance holds the pixels. Bayonne, the first Panoramax city, opens **2026-09-18**; before #110 the word was unknown and every one of its panos was dropped nightly as an unsupported source, which is #101's silent-completion shape. Keyless, so no token, no header and none of the redaction apparatus.
  - **The projection guard is the part that is not obvious.** Panoramax is a commons, not a fleet, so a city's bbox carries other contributors' pictures: 323 of 1,000 in Bayonne are flat 92° photographs (`reports/2026-09-08-panoramax-api.md`). Nothing downstream inspects projection, so a flat JPEG stored as `<pano_id>.jpg` would be cropped with the equirectangular seam modulo and look plausible. A picture is refused **only when its item affirms** a `field_of_view` other than 360 — an unstated one downloads, the #99 rule. `field_of_view` lives under `properties`, unlike `assets`; the first implementation read the top level, so the guard never fired while every other test stayed green.
  - **Absence is a 404 at `/api/pictures/<id>` and a 200 with `{"features":[]}` at `/api/search?ids=`** (measured 2026-09-08). Only the first can found a permanent row, which is why the endpoint choice is pinned by a test rather than left to whoever next reads the API docs. Unlike Mapillary's, the body is read for the catalog's own answer rather than for an auth signature: keyless means there is no "cannot see it" state to mistake for "it is not there", but that says nothing about whether the CATALOG answered at all, so `is_catalog_not_found` requires BOTH measured fields - `status` 404 (compared numerically) and a `message` saying not found. A message-only match is the default 404 body of AWS API Gateway's HTTP API and the usual shape of a hand-written JSON 404, so a WAF, a renamed endpoint or parked DNS would ledger a whole city off a stranger's reply (measured 2026-09-17: the catalog itself answers a malformed id with a 404 whose body is plain text, `UUID parsing failed`, which is exactly a 404 that is not this verdict). The other two permanent verdicts are an affirmed non-360 fov and an item with no `hd` asset - **no `hd` entry in a well-formed, non-empty assets block, which is the only shape `hd_asset_url` returns None for**; an empty block, or an `hd` whose href is missing, null or empty, is the catalog changing shape and raises (every picture measured carries `hd`, `sd` and `thumb`). The id gate in `require_picture_record` folds case, because the catalog does: an upper-case id resolves and comes back canonical lower-case (measured 2026-09-17). Everything else raises unledgered. All three are bounded by `MAX_CONSECUTIVE_PERMANENT_FAILURES` (#113), which Panoramax needs more than Mapillary does: the fov and no-`hd` refusals are both wholesale failures wearing a per-pano face, and only the app's own 360-filter keeps the bbox's 323 flat pictures out of the corpus.
  - Ids are UUIDs — the third id alphabet, after GSV's base64-ish strings and Mapillary's all-digit ids (#46/#55) — and `tests/test_csv_intake.py` pins that all three intakes read them as `str`. Bayonne frames are 5760×2880 and 5376×2688, under the #115 sidecar cap, so no display copy would be written for them even with `common.WRITE_DISPLAY_COPIES` on — and it is off, which is why `_write_display_copy` is the same shape here as in the other two downloaders rather than a bare call: three downloaders reading one switch three ways is how one of them keeps writing.

**CropRunner.py** — extracts per-label crops from downloaded panos.
1. Loads label metadata from `/adminapi/labels/cvMetadata` (`-d`), or a `.csv`/`.json` file (`-f`, case-insensitive extension). Both intakes dedupe on `_label_id_key(label_id)` — the `int` the crop is filed under, keeping the first row, and never deduping a row with no usable id (#170 ops-4 brought the CSV intake onto it), and reporting the rows it dropped in one summary line on both channels with the count and a few example ids (#183) — never a line per row, which is what the JSON side's old `print("Duplicate label ID")` was; the CSV intake reads with `csv.DictReader`, not pandas (#72), so no field's type can depend on what the values happen to look like (the #46 bug class), and requires `REQUIRED_LABEL_COLUMNS` up front, so a header typo is one error naming the file rather than a `KeyError` 200k labels in.
   - **The JSON intake indexes nothing (#164).** `json_to_list` used to read `value["label_id"]` outside any `try`, so one row without it, a null element, or a 200 carrying an error object (iterated as its keys) crashed the whole run. Now every element passes through and the loop's `except (KeyError, TypeError, ValueError, OverflowError)` counts a non-object or incomplete row as one `malformed_row` error, exactly as for CSV (`OverflowError` because `json.load` reads `1e999` and `Infinity` as `float('inf')`, which `int()` refuses with neither of the other three). A top level that is not a list raises `ValueError` naming the source (`-f`: the path, propagated; `-d`: inside the fetch `try`, logged with the URL and exit 1). Dedupe is on `_label_id_key` — `int(label_id)`, the same `int()` the loop files the crop under — so `1`, `"1"`, `1.0` and `" 1"` are one label, and a row with no usable id (absent, null, blank, anything `int()` refuses, by `ValueError`, `TypeError` or `OverflowError`) keys `None` and is **never** deduped, since collapsing two bad rows hides one. The CSV intake uses the same key since the #170 ops-4 follow-up: it used to dedupe on the raw cell, so `'7'` and `'07'` both filed as `7.jpg` (cut twice under `--force`, two provenance rows) and repeated blank/unparseable cells collapsed into one error; `tests/test_csv_intake.py` pins both the other way now. Keying on `int()` there is not #72's type inference — it is explicit, on one column, for the key only; the row keeps its raw `str` and blanks stay `''`. Keep-first holds whether or not the first row is usable, so a malformed row shadows a good one sharing its int, in both intakes (ops-7). The loop's `int(label_id)` also accepts `True`, `3.7` and `'1_0'` from JSON, and from a CSV `'+7'`, `'1_0'` and non-ASCII digits (`'٧'`, `'７'`), which file as `7.jpg`/`10.jpg` and dedupe accordingly — consistent across both intakes and the filing `int()`, and exactly the input set a strict id reader (a follow-up) has to decide.
   - **The label type arrives under one of two names and `resolve_label_type_id()` is the only seam (#123).** cvMetadata sent `label_type_id` (an int) until SidewalkWebpage#4103 swapped the lookup table for a Postgres enum (released v11.11.0, 2026-09-02); every deployment now sends `label_type`, a **name**. On `master` before this, *every* live row raised `KeyError` inside the crop loop's `try`, so a whole city came back as `N errors, of N labels total` and exit 1 with no crops — and the counts invariant reconciled perfectly while it happened, which is why that invariant could not catch it. Both names are accepted, because every archived export carries the id; `LABEL_TYPE_COLUMNS` is the either/or the CSV guard enforces (listing `label_type_id` in `REQUIRED_LABEL_COLUMNS` instead would name a column no deployment sends). A usable id wins over a name, blank counts as absent (a CSV cell is `''`, so preferring on *presence* hands `int('')` a good row), and an unknown type is **one counted error naming the value, never a guessed id** — a wrong id files crops into a real training directory with nothing on disk to say so. **That refusal covers the id path too, and must**: it was a bare `int()` until the 2026-09-18 review, so `label_type_id=99`/`0`/`-3` were accepted and written to `<crop-dir>/99/` as a `success` with exit 0, while the docstring, this bullet and `docs/cropper.md` all three claimed the protection. `LABEL_TYPE_NAMES_BY_ID` is derived from the map rather than written out again, because two hand-maintained copies of one enum is the drift the map exists to stop. `LABEL_TYPE_IDS_BY_NAME` is the upstream enum verbatim, including 8/`Problem`, which is absent from the *data*, not from the enum — `docs/api-fields.md`'s table and the one below both carry all ten rows with the enum name beside the display name, and `TestTheLabelTypeMapMatchesTheDocumentedTable` parses **both** and asserts the pairs, because a table of display names alone cannot catch a swapped id (a `Crosswalk`/`Signal` swap killed only a literal restatement of the dict and left 296 tests green). **Be exact about what that buys: it catches ONE copy drifting, not a wrong pairing.** All three copies — the dict, that table and this one — were written together, so a pair that was wrong when written survives every test; a swap applied to all three still passes. Only `Crosswalk = 9` has outside corroboration (`reports/2026-08-11-mapillary-census.md`, written five weeks before #123 when the id *was* the wire field); `Signal = 10` and `Problem = 8` have none, and the live capture carries no ids at all. Pinning against `LabelTypeTable.scala` or a capture with both columns is what would actually verify the pairing. `samples/cvmetadata-seattle.csv` is a real capture of the live response and is what pins the shape offline, since the suite is network-free.
2. Labels are **grouped by pano**, so each `<pano-dir>/<pano_id[:2]>/<pano_id>.jpg` is decoded exactly once for all its labels — a 13312×6656 pano is ~250 MB decoded and a 16384×8192 one 384 MB (`w × h × 3` bytes). Each label's window comes from `compute_crop_box()`: an integer `CropBox(left, top, width, height, shifted)` centered at `(pano_x, pano_y)`, **3:2**, where **x wraps at the equirectangular seam and y clamps by shifting**, so no crop ever contains synthetic black (#47) — a promise about geometry, not content: black the stored pano already holds is item 3's content check. Width comes from `crop_window_width()` — **sizing rule v2**: `crop_window_fov_deg()` is the rule as an angle (`predict_crop_size()` normalised into the 6656-px frame its constants were fit on, ×`CROP_SIZE_SCALE`, clamped to `CROP_MIN_FOV_DEG`–`CROP_MAX_FOV_DEG` **in degrees** rather than in pixels), and `crop_window_width(pano_y, pano_width, pano_height)` is that angle as an azimuthal span in this pano's pixels — `azimuth_deg_to_px` against the width, because a width is horizontal; the elevation form agrees only on a 2:1 pano and is exactly 2× wrong on a square one (#106 review). `downscale_for_storage()` then caps the cut window at `CROP_MAX_STORED_WIDTH` without ever upscaling it. Every constant is one measured number — see `reports/2026-08-19-crop-sizing-v2.md`; the residual (a y-only rule cannot know how large a ramp actually is) is RampNet #83. **`--sizing-rule v3` is opt-in (#32) and v2 stays the default** until the flip is decided, which means a whole `--force` re-cut of every store (#83) and belongs in the #84 recrop campaign: v3 is `label_depression_deg` → `blend_distance_m` (the lle #3 cotangent blend) → `geometric_window_fov_deg` (`2·atan(W/2d)`, `W = V3_CONTEXT_WIDTH_M`), composed in `crop_window_fov_deg(..., sizing_rule)` and pinned as a composition. `label_depression_deg` is the one seam a #54 tilt term adds to, and `geometric_window_fov_deg` takes metres so a depth-backed distance plugs in unchanged. Every sizing entry point takes a trailing `sizing_rule=` kwarg; `crop_rule.json` and every provenance-manifest row record the **selected** rule (the marker also its `distance_estimator` and the `v3_*` constants), and warns when a constant the selected rule reads moved under the same rule id (`RULE_MARKER_CONSTANT_KEYS`). #170's content check runs on the window whichever rule sized it (`TestTheCheckRunsUnderEveryRule`). A 33-row literal `CropBox` table captured from pre-#32 code (`TestTheDefaultWindowIsByteIdentical`) pins that the default moved no window. See `reports/2026-09-26-crop-sizing-v3.md`.
   - **Degrees↔pixels goes through four named primitives, and the literals 360 and 180 appear nowhere else in the module (#78).** `azimuth_deg_to_px`/`azimuth_px_to_deg` (1.0 of width = 360°) and `elevation_deg_to_px`/`elevation_px_to_deg` (1.0 of height = 180°). Production panos are all 2:1, which makes degrees-per-pixel equal on the two axes and therefore makes a wrong-axis conversion return the *right answer for the wrong reason* — until it meets a pano that is not 2:1, or until the correction is written twice and cancels. That second case shipped in label-latlng-estimation: a depth panel captioned as covering the same window as the photo beside it, stretched by exactly 2, nothing thrown. `TestEquirectUnits` walks CropRunner's token stream, so a new call site that writes the conversion with the constants fails rather than being caught in review. A bare `2 *` at a call site is not seen by that guard, and on a 2:1 pano is even correct, which is what the non-2:1 assertion in `TestTheWindowWidthIsAnAzimuthalSpan` is for.
   - **`label_position_in_crop()` is the one mapping from a label to its place in the crop**, and the thing #54's tilt correction regresses against. It carries the seam modulo, the `shifted` top and the storage rescale; `--mark-label` asks it rather than deriving them. Registration is asserted by planting a unique pixel and reading it back out of the cut crop — never by comparing one derivation against another, which is how the figure above passed review. On the v3 path the pixel→angle step is `label_depression_deg` and nothing else, so a measured #54 tilt is an addend there and every later step takes the corrected angle unchanged.
   - **The rule version lives in the store, not in the run summary.** `write_rule_marker()` writes `<crop-dir>/<city>/crop_rule.json` (the **selected** `sizing_rule` plus every rule's constants, beside #159's `city` and #111's manifest keys) *before* cutting anything, and warns — never refuses — when it disagrees with what is there. A mixed store is the **ordinary** result of changing the rule, since existing crops are the resume marker and are not re-cut without `--force`: run v2 over a v1 store and the new crops are 3:2 while the old stay square, with nothing on disk to say so. The marker is rewritten at the *start* of a run, so an interrupted `--force` run leaves a store whose marker claims one rule while part of it is still the other. Stdout was where this used to go, which on a cron run is nowhere. **The history is sticky, and must stay so (#157 review):** `rules_seen` and `constants_seen` are append-only, and the warnings fire on every run whose rule or constants are not the only ones seen — a `--force` run included, since a forced pass cannot prove it reached every crop (the same reason #153's `provenance_manifest_no_known_gap` never turns back to true). Before them, one warned `--sizing-rule v3` run over a v2 store rewrote the marker to `v3`, and every later run compared against that and was silent over a store of v2 crops — and a v2/v3 mix is 3:2 on both sides, so the marker is the only evidence. An unreadable marker is warned about, recorded as `unknown` for good, and kept aside as `crop_rule.json.unreadable-<stamp>`, never silently replaced (under `main()` a non-object marker is refused earlier by `check_store_city`, so what reaches that path is an object whose rule fields are malformed; its city and manifest keys are still carried forward). `_read_rule_marker` type-checks **only the rule's own fields** (`RULE_MARKER_SCALAR_KEYS`): the manifest's gap flag is a JSON bool, and checking every field called every marker a manifest-era run had written unreadable. Anything that rewrites the marker (`_record_manifest_gap`) must carry every key forward. **The reset is removing `rules_seen`, `constants_seen` and `previous_crop_rule_version` from the marker — never a crop, and not the whole file — after the whole store has been re-cut under one rule;** deleting the file would also drop the store's city (re-adopted from `--city`) and turn the manifest's gap record into `null` for good. Before a whole re-cut that would make a mixed store read as clean, which is why nothing does it automatically; the plain-run warnings name that reset beside `--force`, because after a whole forced re-cut they still fire and "re-run with --force" alone is a loop.
   - **`reports/scripts/crop_rule_v1.py` is the one frozen copy of the old rule**, used by the sizing study and by the two census tests whose reports were *measured* under v1. It is a record, not a rule anyone runs — the resolution defect in it is the subject of the v2 report and must not be "fixed".
3. Two preflights skip a label rather than emit a quietly wrong crop: a metadata/image **dims mismatch** (`dims_mismatch`) and a `pano_y` **outside the image** (`out_of_frame`).
   - **The content check withholds a mostly black window (`black_content`, #164).** Geometry says where a window is, never what is in it, and a stored pano can hold black where imagery should be — #156's D4 stitch (a frame reported larger than Google serves: ~34% black along its right and bottom 19%) or a pre-#68 fallback — which passes the stitcher's own whole-pano 50% guard. So `make_single_crop` measures the window **exactly as `extract_crop` returns it**, before `downscale_for_storage` and before `--mark-label`, with `downloaders.common.black_fraction` (exact-zero luma, the stitcher's primitive, moved out of `gsv.py` into `common` beside the other shared image primitives, where a caller outside `gsv.py` looks for it — not an import boundary, since `downloaders/__init__.py` imports `gsv`, so CropRunner's `from downloaders.common import ...` loads `gsv`/`config`/aiohttp/numpy anyway; `gsv._black_fraction` is an alias of the same object and a test asserts it). `fraction > CROP_MAX_BLACK_FRACTION` (0.5, strict like the stitcher) raises `CropWindowMostlyBlackError` before anything is written. 0.5 is a measurement, not a tune: inside a large black JPEG region luma is exactly 0 and ringing stays next to the edge, so a label inside a band whose window is not shifted gets at least half black rows, while JPEG noise keeps a night scene or a black car off 0 — a label within the ringing margin of a band edge, or a crop under half black, is written knowingly (table in `docs/cropper.md`). **A bottom band is caught only deeper than H/6, under either sizing rule:** near the nadir the window is clamped at `CROP_MAX_FOV_DEG` (90° wide, so 60° of elevation at 3:2: a third of the pano's height) and shifted to end at the bottom row, so every label in the lower sixth gets the same window and its black share is band depth over H/3, wherever the label sits. The D4 band (18.75%) clears that by ~6 points; a 10–15% band is written as `success`, 29–45% black. v3 reaches that ceiling from 38.9° of depression and the shift starts at ~60° under both, so its nadir window is the same box and H/6 is one figure, not a v2 fact; the band-edge table (y → black share) *is* per rule and `docs/cropper.md` gives both columns. Two tests pin it against the geometry (`test_at_the_nadir_a_bottom_band_is_caught_only_deeper_than_a_sixth_of_the_pano` and its stored-JPEG twin, each parametrised over both rules), and `TestTheCheckRunsUnderEveryRule` pins that the check sits between `extract_crop` and `downscale_for_storage` for v3 too. **It is a disjoint bucket, not an error and not an annotation**: like `dims_mismatch` it is something the run refused to trust, so no exit-code change and no `SYSTEMIC FAILURE`; nothing is written (no crop, no `.part`, no provenance row), so a re-run cuts it once the pano is repaired; one `crop.log` line per label under its own `WarningBudget` kind, plus one both-channel summary line when nonzero, because a 100% `black_content` run otherwise exits 0 silently (#101's shape). **It runs only on a crop about to be written** — after the `skipped_existing` branch — so crops on disk are never re-judged, and under `--force` a withheld window keeps the old crop byte for byte and counts `stale_kept` as well; the stale_kept sentence gains an addendum rather than a rewording. **Known limit, pinned by a test:** a label *outside* a D4 stitch's bands gets clean imagery at the wrong scale — 0% black, dims agree — which no crop-level check can see; the pano-level check belongs on the downloader/refetch side (an eager decode plus a ~134 MB luma copy per 16384×8192 pano here, and a threshold that would need calibrating against real zenith/nadir caps). Not recorded in `crop_rule.json`: a crop that passes is byte-identical to one cut before the check.

Writes to `<crop-dir>/<city>/<label_type_id>/<label_id>.jpg` through `atomic_output_path` (#159: `-o` is a root holding one self-contained store per city - `main()` composes `store = os.path.join(args.o, args.city)` and everything below it, `run()`/`bulk_extract_crops()` included, takes that one store plus `city=`, so the ~160 `bulk_extract_crops` test calls needed no change). By default existing crops are the resume marker (`skipped_existing`) and are **not re-cut**, so a store cropped before #47 or under rule v1 keeps those crops. **`--force` (#83) re-cuts them instead** — the repair for a rule change — and the same `atomic_output_path` is what keeps the old crop whole until its successor is renamed over it. It re-cuts only labels that reach the write: a label skipped as `missing_pano`/`dims_mismatch`/`out_of_frame`, or absent from the metadata, keeps whatever crop it had. Each of those three cases is counted when its crop is on disk (`stale_kept`, #153 m2 and final F3) and said on both channels, because all of them come *before* the exists check and so leave an old-rule crop under a marker naming the new rule; deleting such a crop is Jon's call, not a fix, and nothing does it. More generally, a label the run did not write (including `black_content`, and a pano that opens but cannot be decoded) keeps its old crop, and under `--force` counts `stale_kept` when one is on disk (#164). Rotating `crop.log` lands in the city's store next to the crops, not the root and not the CWD.
   - **`refuse_production_crop_store()` refuses a destination that looks like the store SidewalkWebpage serves (#83), before ANY write.** That store is `<root>/<city-id>/<LabelType>/crop_<labelId>.png` — canvas captures the browser took at label time, irreplaceable, and nothing to do with this tool's formula crops. Refused on an immediate subdirectory named for a label type (`LABEL_TYPE_IDS_BY_NAME`, case-folded), a `crop_*.png` up to two levels down, so `-o` at the root, a city or a type directory is caught, or a directory the scan cannot list (a `PermissionError` or Windows' `WinError 1920`, at the `scandir` or partway through; see `_is_unlistable`), named in the message — what cannot be read cannot be ruled out. A label-type shard `_store_holds_crops` cannot list is the same error one step later and is **not** a refusal: `main()` reports `CropStoreUnlistableError` on both channels and exits 1 (#153 final F6). **It raises, never warns** — `ProductionCropStoreError`, which `main()` prints, logs at ERROR and turns into exit `EXIT_REFUSED_DESTINATION` (3, not 1). The two layouts are disjoint on every name component today, and that is a coincidence of naming, not a guard. Three placements are load-bearing: first in `bulk_extract_crops` (before its `makedirs` and `write_rule_marker`), and first in `main()` (before it creates the store and opens `crop.log` there — without that, the refusal itself would drop a `crop.log` into the production store). **`main()` calls it twice since #159, on `-o` and on `<-o>/<city>/`**: both layouts are city-first now, so depth no longer separates them, only names do (numeric dirs + `.jpg` vs `LabelType` dirs + `crop_*.png`); from `-o` a production city directory sits at depth 1, where the name signal is not read, so one whose type directories are still empty passes the root scan and is caught only at the store. The scan never descends into all-digit directories: those are a formula store's ~400k crops over sshfs, and the production layout never puts a capture in one. The file signal is the `crop_` prefix **and** `.png` — our own `crop_rule.json` shares the prefix.
   - **One store per city, and the store remembers which — `check_store_city()` (#153's stopgap, kept by #159).** Crops are `<label_type_id>/<label_id>.jpg` inside a store and `label_id` restarts per city, so two cities in one store collide: without `--force` city B gets A's crop as `skipped_existing`, with `--force` B **replaces** A's crop. #159 removes the collision by construction (each city its own `<crop-dir>/<city>/`); the recorded city still catches a store under the wrong name (renamed or copied by hand). `--city` is required (strict `city_id` regex plus an active row of `log_analyzer/cities.csv`; a city spelled two ways would be two stores), `write_rule_marker` records it in the store's `crop_rule.json`, and `main()` calls `check_store_city(store)` before the store or `crop.log` exist — refusing a different recorded city **and an unreadable marker** (unreadable is not "no city") with exit 3; `bulk_extract_crops` checks again when handed a city. A marker with no city adopts the one given, so a pre-#159 store already sitting at `<X>/<city_id>/` needs no migration (`-o <X> --city <city_id>`); `city=None` below `main()` carries the recorded city forward rather than erasing it. Every refusal is asserted on the bytes of the whole tree (`tests/test_crop_store_city.py`).
   - **A pre-#159 flat root is refused, never cropped into — `refuse_legacy_crop_root()` (#159).** `main()` runs it right after the `-o` production guard: `legacy_layout_signal()` does one `scandir` of `-o` and stops at the first all-digit directory or `LEGACY_ROOT_FILES` file (marker, manifest, set-aside manifest; `crop.log` alone is not a signal); it returns a `LegacySignal(kind, description)`. An all-digit directory that is not a label type's (`_is_label_type_shard`) is still a signal, of kind `LEGACY_STRAY_DIGIT_DIRECTORY`, and its message says only "move it out of -o by hand, then re-run" - not "a pre-#159 store", not the migrator, which would list it `LEFT` and exit 1 with nothing moved (final review M1). Exit 3, `--force` included, on both channels; for the other two kinds it names what it found and `migrate_crop_store.py <o> --city <city> --dry-run`; when `-o` is named for `--city` (`city_named_directory()`: after normpath, and again after realpath, so a trailing slash or a link counts) the message says only "point -o at its parent" and **never offers the migrator**, which would nest the store as `<city>/<city>/` (it refuses that root) and cannot sort out a store several cities were cut into. Order in `main()` is load-bearing: parse → production guard on `-o` → legacy check → production guard on the store → `check_store_city(store)` → `makedirs(store)` → `crop.log` → `run(store)`. Two facts keep the signal sound, and `tests/test_crop_store_layout.py` pins both against the committed roster: no active `city_id` is all digits, and none is a label-type name.
5. `--mark-label` draws a dot at the label position **inside the crop**, never on the shared pano, and follows the label through both transforms. It is **off by default**: it was a `MARK_LABEL = True` module constant until #48, so every crop this tool produced before then has a (128, 0, 0) dot burned over the feature of interest.
6. **Nothing in the crop loop is fatal.** (The destination guard in item 4 is fatal on purpose, and runs before the loop — it is a verdict about `-o`, not about a label.) The counts reconcile on every path including re-runs and `--force` runs — `success + skipped_existing + missing_pano + dims_mismatch + out_of_frame + black_content + errors == total` (`shifted_vertically` and `recut` annotate a success and `stale_kept` a label `--force` did not write, so they are deliberately *not* in that sum; a re-cut is a `success`, and `recut` counts only a success that replaced a crop already on disk, not every success under `--force`). A corrupt pano, malformed row, or failed write is one counted, logged error and retries next run. A pano whose header opens but whose body will not decode (#164) is decoded **once, lazily**, by the first label that reaches the write — the preflights and `skipped_existing` read only the header, so a finished store never decodes and a label's bucket does not depend on its position — and after a failure every label on it that reaches the write is an error (plus `stale_kept` under `--force` with a crop on disk) with **one** `cannot decode` line per pano under the `cannot_open` kind; before, Pillow's retained `im.tile` re-decoded the whole file per label and each logged a `crop_failed` line, which spent the budget real write failures need. `main()` exits 1 if `errors` is nonzero — **not** on `missing_pano`/`dims_mismatch`/`out_of_frame`/`black_content`, which are metadata or imagery the run refused to trust rather than work it got wrong.
7. **A run where errors DOMINATE gets a signal of a different shape (#136).** `systemic_failure_line()` appends one `SYSTEMIC FAILURE` line to the summary, on **both** channels, when `errors >= SYSTEMIC_ERROR_FRACTION * total` and `total > 0`. #123 is why: the bookkeeping was perfectly healthy (`errors == total`, the invariant held, exit 1) and the run still read as noise, because 260,000 identical per-row `WARNING`s differ from three of them only in length — and CropRunner is hand-run, so no cron mail carries the exit code anywhere. Three things about it are load-bearing. **It is a second *reading* of the counts, never a bucket**: it takes the finished dict, returns a string or `None`, and touches nothing, which is what keeps it out of the invariant's way — a mutant that increments a counter alongside it fails every one of the crop loop's error-taxonomy tests plus the reconciliation test written for it (don't quote a count here — the delta that added the alarm's own tests cannot change it, and two reviews quoted two different numbers). **Neither guard is what keeps a quiet run quiet — the threshold test is.** For any `total > 0`, `errors <= 0` already satisfies `errors < fraction * total`, so 100% `missing_pano` and 100% `skipped_existing` are silenced by arithmetic. `total <= 0` is the only clause with a distinguishing input (`{'total': 0, 'errors': 1}`, where the division raises) and it short-circuits first, so on an empty run `errors <= 0` is never even evaluated; `errors <= 0` is **redundant at the shipped fraction**, kept as a statement of intent, and its mutant is equivalent rather than unkilled-by-oversight. Two rounds of review got this wrong in opposite directions before it was written as a truth table in the docstring — read that table, not a causal story. **The denominator is `total`, deliberately**, so 100% `missing_pano` (the scrape lags) and 100% `skipped_existing` (a finished store) stay silent. Three costs, not one: a mature store whose handful of new labels all fail to write is a small fraction of a large total; `missing_pano` **dilutes** the denominator, so a genuinely systemic write-side failure on a half-scraped city can sit under the threshold; and a run that is 100% `dims_mismatch` or 100% `out_of_frame` is silent **and exits 0**, because those are skip buckets (100% `black_content` also exits 0, but is said on both channels — item 3) — the silent-completion shape #101 exists to hate, reachable if a schema move changes what the dims or `pano_x`/`pano_y` fields mean. The fraction is 0.5 because that is where errors stop being a minority outcome — 100% alone is defeated by one label of noise, ~10% sits inside what an ordinary bad night reaches. `docs/cropper.md` carries the reasoning.
8. **`crop.log` is bounded under a flood (#139), by lines and never by counts.** #123's 260,000 whole-row warnings were ~100 MB through the 10 MB × 3 rotation, which destroyed the log's history and ~70% of the flood itself. The malformed-row line names `label_id`/`pano_id` first (`?` if unreadable) and clips the reason and the row to `LOG_ROW_REPR_MAX_CHARS`; every per-label warning goes through one `WarningBudget`, `LOG_WARNINGS_PER_KIND` lines per kind per run, one notice at the first dropped line and one total at the end, written *before* the `SYSTEMIC FAILURE` line so that stays last. Two things are easy to break: **the budget never sees the counts dict** — each bucket is incremented unconditionally before the call, and a test asserts the counts are identical at caps 0, 1, 2 and 1000 — and **the budget is per kind**, so a flood of one kind cannot hide the first lines of another. `missing_pano` is deliberately outside it (the normal state of a lagging scrape, one line per pano). `black_content` (#164) is its own kind, so a store full of black bands cannot hide another kind's first lines. stdout is untouched: the cap is a `crop.log` concern and a test pins the printed output byte-identical across caps.
9. **Every crop this tool cuts gets a row in `<crop-dir>/<city>/crop_provenance.csv` as it lands (#111)** — `city, label_id, pano_id, source, copyright, license, crop_rule_version`, through `ProvenanceManifest`: one handle for the run, a row appended right after `counts['success'] += 1`, the ledgers' contract, so a killed run leaves a truthful partial file: every row describes a crop this tool cut, and a kill can leave at most the crop in flight without its row (a torn row is cut back at the next open and recorded as a gap). One CropRunner per store — nothing locks the manifest, and a second run's open would cut this run's in-flight row. Load-bearing: **a field the row does not state is written empty, never inferred** — cvMetadata sends none of the three today, `REQUIRED_LABEL_COLUMNS` did not grow, and tests on all three intakes pin both halves; the column is **`copyright`, not `producer`**, because that is the app's own name for the producer credit (`pano_data.copyright`); **a failed append is not an `errors` entry** — the crop is the resume marker, so a plain re-run can never write the row and counting it would put one label in two buckets — it is a `provenance_unrecorded` warning under the #139 budget plus a count on both channels, and the exit code does not move. **A row reaches the file whole or not at all (#153 M2)**: the handle is *unbuffered* and each row is one encoded line, because a buffered writer kept a failed row and flushed it with the next one, making the unrecorded count false; after a failed append the handle is dropped and reopened at once (#153 final F4), so no run ends on its own torn row. **Every open cuts the file back to its last `\n` (#153 n2)** — never appends one, since a tear inside a quoted `copyright` would put that newline inside the open quote and swallow every later row — and writes the header when nothing is left. **The loop sits in a `try` whose `finally` closes the manifest (#153 M1)**, and a close that raises is said on both channels rather than raised: an unguarded close on a full store used to take the summary, the unrecorded total and the `SYSTEMIC FAILURE` line down with it. Crops cut before the manifest have no rows and are not re-cut without `--force`, so `write_rule_marker` records `provenance_manifest_started_under` and `provenance_manifest_no_known_gap` when the manifest is started (the latter from `_store_holds_crops`, which stops at the first `*.jpg` in a numeric shard) and carries both forward. **The gap flag only ever goes true → false (#153 M3)**: `_record_manifest_gap` flips it, in the same `finally`, on an unrecorded row or a failed close, and at the first open on a torn row — **before** cutting it (#153 final F1), since the fragment is the only evidence and a SIGKILL runs no `finally`; a record that fails there stops the run with nothing cut. It never overwrites a marker it cannot read (#153 final F2): only an absent one is rebuilt around the flag, since rebuilding a present one lost every rule key. Nothing turns the flag back — `--force` included, since the marker cannot tell that a forced pass reached every row-less crop. It was `provenance_manifest_complete_from_start` and renamed because it records what runs reported, not coverage: coverage is rows against crops on disk, and `(city, label_id)` is the cross-city key for rows (`city` is the first column; `tests/test_crop_store_layout.py` pins that combined manifests are unique on it and not on `label_id`). A backfill for pre-manifest stores is out of scope. **A manifest whose header predates `city` is set aside, never appended to (#159 step 1).** `_open` writes a header only into an EMPTY file, so it trusts whatever header a non-empty one carries, and seven-field rows under the old six-field header read shifted by one column with nothing raised. `set_aside_pre_city_manifest()` runs before `write_rule_marker`: the `PRE_CITY_PROVENANCE_COLUMNS` header is moved whole to `crop_provenance.pre-city.csv` (never over an existing one; its rows are never given a city, since a pre-#159 root may mix cities) and named in the marker's `provenance_manifest_pre_city`; any other header raises `ProvenanceManifestHeaderError`, exit 3, before any crop. An unreadable manifest is left to `_open`'s own failure. `docs/cropper.md` has the consumer warning: Mapillary and Panoramax crops carry a licence that must follow them into a dataset.

**scrape_queue.py** (#101) — the nightly driver: one cron line that walks a city manifest and starts each city as soon as the last one exits, replacing 53 hand-picked crontab slots. Same extracted shape as the runners (`build_parser()` / `configure_logging()` / `main(argv=None)` behind a `__main__` guard), so it imports inertly and tests drive `main()` in-process against a stand-in runner script.
1. **It replaced a ring, not a schedule.** Slots were staggered across the whole UTC day and had wrapped, so 32 of 53 cities ran 07:00–19:00 Pacific — the working day on the store and the app hosts, which are in Seattle regardless of where the city is. The schedule follows DST because the **box's timezone** is `America/Los_Angeles` (`timedatectl`), not because of `CRON_TZ` — the cron line carried that for eleven nights and Ubuntu's Debian-derived cron silently ignored it, so the fleet ran at noon Pacific until 2026-09-17 (`docs/downloader.md`, Nightly deployment).
2. **Two budgets that compose, and the composition is the point.** `--max-runtime` is the window and gates *starting* a city (never interrupts one, same rule as the image phase, #51); `--city-max-runtime` is passed through as the runner's own `--max-runtime` and hard-killed `--kill-grace` minutes later. The city gets `min(the two)`: the city cap alone lets the last city run past the window, and the remaining window alone lets the *first* city eat the whole night — the head-of-line problem serialising introduces.
3. **The kill is the backstop, not the mechanism.** SIGTERM first, because `DownloadRunner` translates it into `sys.exit(143)` and its `finally` still writes the `log.csv` row (#49); `SIGKILL` only if that is ignored. **A stop of the queue landing during that SIGTERM wait kills the city at once (#161)** — `stop_process` runs inside an `except` handler at both call sites, so the `SystemExit` used to escape past every sibling handler, never send SIGKILL, release the lock and leave tomorrow's queue running beside an orphan. The kill costs that city's `log.csv` row; nothing waits after it, so a third signal cannot interrupt the fix.
4. **The lock is advisory (`flock`/`msvcrt.locking`), never an `O_EXCL` file**, and defaults to local disk rather than the store. The OS releases it when the holder dies — a lock that outlived a crash would silently stop the whole fleet, which is worse than the overlap it prevents — and the store is a network mount whose lock semantics are not guaranteed.
5. **A city the window never reached exits nonzero**, like a failure — and so does **any run condition** (item 9). The exit code is the only unattended alarm, and a fleet quietly completing 40 of 53 cities a night is exactly the silent failure #101 is about. **The exit is only an alarm if something delivers it** — cron's own mail never did on the production host (no MTA, 2026-09-01 to #141), which is why the crontab line runs the queue through `cron_notify.py` (below; `docs/ops.md`, Hearing about a bad night).
6. `--cities` has no default (deployment fact, same reasoning as `resolve_sftp`'s host/base), a `#`-prefixed row is skipped (replacing "comment the crontab line out"), and the manifest carries `fqdn` next to `city_id` because **there is no rule that derives one from the other** — `seattle-wa` is served by `sidewalk-sea`.
7. **Extra passes spend the window on whoever still has work (#43).** Pass 1 is the guarantee and is unchanged; then, while a full slot remains, the cities whose previous run *stopped on a budget* are run again with `max(slot, remaining / cities_left)`. Measured before this existed: 477 of 690 minutes used, 13 cities complete, the five largest 240–463 nights out. The floor at a slot is load-bearing (5.5-minute shares would zero every image phase under `--min-depth-runtime 6`, and sub-minute ones can kill a city inside its pano-list fetch); a later pass never yields `skipped_deadline` but a crash in one still exits 1; `--single-pass` opts out and `--only` implies it. A city re-run in a night writes one `log.csv` row per run, which the analyzer does not expect until #124 — its same-day rule fires at INFO per re-run city and its 30-*row* window becomes ~10 days.
   - **Who has work is READ FROM THE RUNNER, never from elapsed time.** The queue passes `--run-summary-file`; `DownloadRunner` writes `{image_stop, depth_stop}` and only `max-runtime` (in either phase) means "more time would have helped". Timing the subprocess is wrong in **both** directions, because the queue measures spawn-to-exit while the runner's budget clock starts after its pano-list fetch: a *complete* city whose prologue outlasts its slot read as "has work" forever and burned a slot every pass of every night, and a city whose image phase stopped on its `--min-depth-runtime` share while depth finished early read as "finished" at minute 6.4 of 12 with a live backlog. `blocked` / `consecutive-failures` / `max-requests` are reasons **not** to re-run and must each arrive as themselves; no summary at all falls back to the old elapsed rule, which is at least a *necessary* condition — and that case is **not** "an older runner": a `DownloadRunner` without the flag refuses it (argparse, exit 2) and is booked `failed`, so a queue newer than its runner fails the whole fleet rather than degrading, and a runner killed mid-run exits nonzero too. What reaches the fallback is an `ok` run whose summary could not be written, or an operator's own `--run-summary-file` after `--`. `STOP_MAX_RUNTIME` is repeated in three modules and pinned equal by tests, because a rename would silently turn every city into "finished".
   - **`--min-depth-runtime` is scaled with the budget**, since it is a *share* of `--max-runtime`: an unscaled 6 against a 120-minute endgame slot gives images 114 minutes and depth the same 6 it had in pass 1. Scaled up only, never down — pass 1's last city can be clamped below the slot, and enlarging the reservation towards a smaller budget zeroes the image phase.
   - **Conditions are reported one line per KIND, never per city (#161, `conditions_report`).** The night sends one message, and a refusal followed by 40 stood-down cities is two facts: each line names the first city (its pass when not 1, and its detail) and lists the rest, a city once per kind across passes. Lines go after the outcome lines and before the manifest gap lines, log at ERROR, and the totals line gains `, conditions: <kinds>` so "N/N cities ok" never reads clean above an exit 1.
   - **`summarise` has two denominators on purpose.** "N/M cities ok" counts pass 1 (a night that re-ran one city five times is still a fleet of M), while the failure counts beside it are over *every* run — counting only pass 1 there printed `0 failed, 0 timed out` on a night that exited 1. Non-ok lines are grouped `failed → timed_out → skipped_deadline` so crashes lead, with run order kept inside each group.
   - **A stop still prints the summary.** `run_queue` takes `results` as an out-parameter and `main` reports from an `except BaseException` before re-raising: the passes make the queue occupy the whole 690-minute window, so the interval in which a kill can land is now the entire night.
8. **The manifest is cross-checked against `/v3/api/cities` after the fleet runs, keyed on `city_id` (#130).** `laurens-ia` and `bayonne-fr` launched with no row and the queue ran 53/53 green for six nights. Every deployment serves the same roster; `check_manifest` asks the first host that answers (tonight's `ok` cities first, most recent first, `ROSTER_MAX_HOSTS` = 3) and names every city with no row, **private ones included (#143)** — on the totals line, above it with the failures, at ERROR in `scrape_queue.log`, and in the exit code. **An unserved roster is reported the same way** — its ERROR line is a gap line and the totals line says `manifest not cross-checked` — because `summarise`'s rule is that a clean totals line is never printed above an exit 1 the runs did not earn; until the 2026-09-18 post-merge review that line went LAST, under the totals and every extra-pass line, and the totals said nothing. On a dry run it is advisory and stays under the plan. **The key is `city_id` because the app reads `<pano.images.directory>/<city-id>/` with its own id, the one the roster reports** — a row under any other name (`bayonne` for `bayonne-fr`, one afternoon in 2026-09) scrapes into a directory the app never looks at, and keying on fqdn would have let it through. Three rules that are easy to "simplify" away: **a roster nobody serves also exits 1 on the nightly path** (decided 2026-09-17: the hosts asked just served `/adminapi/panos`, so it is a broken check, not weather — a check silently skipped every night is the failure it exists to prevent; `--dry-run` keeps it advisory); **a `#`-disabled row is credited only while it still names the city's host**, because `csv` splits a prose comment on its commas and `# laurens-ia, bayonne-fr launched…` reads as a row for `laurens-ia` — and where the roster gives no host to match — every **private** city, whose `url` is `null` (`buildCityObject` writes `JsNull` deliberately), and a public one whose url is null or unparseable — only while the column is *shaped* like a hostname and is not another roster city's published host (`_HOSTNAME_SHAPE`, `_disabled_row_credits`), the strongest evidence there is with no host to match (residual: a comment of the exact form `# zurich, ops.md` reads as a decision); and **visibility does not decide membership** — the check was public-only until 2026-09-19, with 20 of 59 deployments private and a private launch as silent as Laurens was, so the study and scratch deployments that are never scraped each carry a `#` row and the manifest records the decision (a test asserts the reported set is the same with the visibility filter deleted). A shared secret to get the private urls was considered and rejected: it would buy the hint, not the detection, and those urls are in SidewalkWebpage's public `conf/cityparams.conf` anyway (2026-09-23). `parse_roster` accepts only the measured shape (#99's rule, including a `public`/`private` visibility on every entry and at least one public city — an empty or all-private answer is a broken one, and accepting it would print "checked against 0 public cities" forever), and `_open_url` builds an opener with an empty `ProxyHandler`, the `trust_env=False` of `DownloadRunner`'s session, for the same host's sake.

9. **An ok city can still fail the night (#161).** Conditions are a separate axis from outcomes: `read_run_conditions` reads the summary's `conditions` onto `CityResult.conditions` (default `()`), the outcome stays `ok` (so `stopped_on_budget`, `roster_hosts` and the `N/M cities ok` count are untouched and a stood-down city keeps its re-run eligibility), and `exit_code_for` fails the night on **any** condition — because production delivers only nonzero exits, a condition that did not fail the night would reach nobody. Reading rules: no file / no key / bad JSON is `()`; a present-but-malformed list (including a code that is only whitespace) is one `conditions-unreadable`; an unknown code is kept, with its whitespace collapsed to single spaces so a newline in it cannot split the summary line. An `ok` run with no readable summary gets `no-run-summary` (a check that did not run has not passed) — which means an operator's own `--run-summary-file` after `--` now alarms nightly. `CONDITION_LABELS` repeats `DownloadRunner.RUN_CONDITIONS` rather than importing it (`STOP_MAX_RUNTIME`'s reason) and a test pins the two sets together. The per-city line gains `; conditions: <codes>` and logs at ERROR.

10. **The store marker is positive evidence that the store is mounted (#161).** `<store-root>/.pano-store`, created once by the operator on the remote store, checked with `isfile` (a directory is not a marker; a dead FUSE mount's `ENOTCONN` reads as unmarked). Missing at startup: `main` prints one stderr line and returns **5** (`EXIT_STORE_NOT_MARKED`; not 4, which `cron_notify` owns) **before `configure_logging` and before the lock**, and no longer `makedirs` the store root — logging would create `scrape_queue.log` on whatever is there, the root disk when the mount is down. Missing before a city start (`run_queue(store_check=...)`, every city, every pass): the city is booked `store_missing`, never started, never re-run, printed as one grouped line that leads the summary, and the night exits 1; the check is per city, so a returning mount is used. `os.path.ismount` was rejected (passes a wrongly mounted fs, fails a store that is a subdirectory of a mount). `DownloadRunner` deliberately does not check it — hand runs into arbitrary dirs are documented. `--dry-run` also probes, advisory only, whether the cities' interpreter can import `streetlevel` (`probe_streetlevel`, a child process; skipped under a passed-through `--skip-depth`, never run on the nightly path, where the runner reports `depth-unavailable` itself). `BASH_ENV` (the Mapillary token) is deliberately **not** probed: an interactive dry run does not source it, so it would always read unset.

**cron_notify.py** (#141) — the alarm channel: cron's mail-on-output rule with the delivery made a command. Runs the queue with stdout and stderr merged, streams every line through to its own stdout, and when the queue exits hands the capture to `--sink` — by default **if there was any** (any output, not nonzero exit alone, so a `WARNING` on a clean night still travels), or with `--only-on-failure` only on a nonzero exit, which is what production runs (Jon, 2026-09-18: a message on a bad night, silence on a good one; a failure that printed nothing is still delivered with a body saying so, and the `--log` line is what distinguishes a quiet night from a wrapper that never ran). The sink gets the body on stdin and in `$NOTIFY_BODY_FILE` (awscli reads it with `file://`, sidestepping the 128 KB single-argument limit), `$NOTIFY_SUBJECT` (`<name>: exit N on <host>`, forced ASCII/one line/≤100 chars — SNS refuses the *whole publish* otherwise) and `$NOTIFY_EXIT`. Production's sink is `aws sns publish` under the instance role: no secret on the box, no mail-service onboarding, and nothing in this repo imports AWS — the tests' sink is a Python script that journals what it was handed. Four rules, each with a test and a mutant that dies:
1. **The exit code is the queue's own.** The one code added is **4** — queue exited 0 *and* the sink failed — because a wrapper that swallowed its own delivery failure would be #141's bug one layer up. A queue exit 1 plus a sink failure stays 1 (the night's verdict is the more important fact); both print `cron_notify: sink failed` on stderr, which on this host goes nowhere, so `--log` writes one line per run (`<stamp with offset> exit N published|nothing to publish|sink failed ...`) and that file is part of the morning check. A queue that cannot be *started* is reported **through** the sink, exit 127.
2. **It is outside the queue, not a `--notify-command` inside it.** `run_city` spawns `DownloadRunner` with inherited stdout, so the runners' narrative is only visible from outside; and a queue that crashes before its summary must still be reported. The wrapper is the one process that sees both.
3. **SIGTERM is forwarded exactly once, however many arrive.** The queue turns SIGTERM into `sys.exit(143)` and stops the city it is supervising on the way out; a second one landing during that unwind escalates the stop to SIGKILL (#161) and loses the city's `log.csv` evidence row. The wrapper's argv contains `scrape_queue.py`, so the stop recipe in `docs/ops.md` is the anchored `pkill -TERM -f '^\S+/python \S+/scrape_queue\.py'`, not `pkill -f scrape_queue.py` — that would signal both, and the wrapper would forward one more.
4. **`--max-bytes` (200 000) keeps the head and most of the tail, cut on line boundaries, with an exact `N bytes omitted` marker.** SNS caps a message at 256 KB and a backlog night prints one line per pano; the queue's summary is at the *end*. The message is the alarm; `scrape_queue.log` and each city's `scrape.log` are the record.

**log_analyzer/analyze.py** — ops monitoring for the nightly scrape; shares no code with the runners.
1. Reads `log_analyzer/cities.csv`, pulls each city's `log.csv` off the pano store with `sftp -b -` (the store's restricted SFTP subsystem doesn't speak the SCP wire protocol), and caches it in the gitignored `log_analyzer/logs/`. Connection settings come from `PS_SFTP_*` env vars or matching flags — host and base path are required with no defaults, since a wrong default would silently analyze the wrong store.
2. Parses the 19 positional columns by position (`LOG_COLUMNS`), tolerating a present-or-absent header: `write_log_csv_row` never writes one, and production files get theirs by hand at city setup. **The intake is `csv.reader` plus explicit padding, not `read_csv` (#43)** — measured on pandas 3.0.5, `read_csv(names=...)` cannot parse the file every production city has since field 19 shipped (an 18-name hand-written header, years of 18-field rows, then 19-field rows) under either engine; every city would have read CRITICAL "Could not parse log". Blank fields stay `NaN` — a crashed run must never read as a quiet one — so every check guards against NaN rather than coercing to `int`.
3. Prints per-city issues at CRITICAL/WARNING/INFO and exits `1` if anything is CRITICAL, so cron's mail-on-failure alerts (on a host that can mail — the scraper box cannot; `cron_notify.py` would serve this script the same way). Thresholds are module constants near the top.
3a. **Cross-checks `cities.csv` against `/v3/api/cities` (#133), and `log_analyzer/roster.py` is a deliberate COPY of `scrape_queue`'s roster machinery.** Not an import: this is ops monitoring that has to keep working when the runners are broken, so it must not depend on the fleet driver it watches — a test pins both `parse_roster`s against one fixture so the copy cannot drift. Same rules as #130/#132/#143 (comparison not auto-discovery, keyed on `city_id`, **private cities included**), and the same refusal to fail open: no host serving a roster is CRITICAL, because a check silently skipped every night is the failure it exists to prevent. The hosts **default to `sidewalk-sea`, then `sidewalk-chicago`** (`DEFAULT_ROSTER_HOSTS`, tried in order; `--roster-host`/`PS_ROSTER_HOST` take a comma-separated list that replaces them) — unlike the SFTP host/base, whose missing default is deliberate, every deployment on the current release serves the same roster, so the host decides only whether the check runs. `tests/test_log_analyzer.py`'s autouse `_no_roster_network` makes `roster._open_url` raise an *uncaught* error, because with a default a forgotten `fetch_roster` stub would otherwise reach production and still pass. The fetch is **unauthenticated on purpose**: a keyed roster carrying private cities' urls was rejected on 2026-09-23, because those urls are only withheld from crawlers (SidewalkWebpage#5259) and sit in SidewalkWebpage's public `conf/cityparams.conf` — a key would guard nothing secret. Two things are specific to here. The gap **does not enter `results`**, whose length is the `N cities checked` denominator — a fleet fact counted as a city makes the denominator lie, which is `summarise`'s lesson one module over. And the `#` opt-out **requires the literal `not-monitored:` marker**, because unlike the queue's manifest this file has no host column to check a disabled row against, so an id-only rule would credit the prose comment (`# laurens-ia, bayonne-fr launched…`) that `csv` splits into a row for the very city it names. `washington-dc` is why this shipped: re-launched, live, serving `/adminapi/panos`, and with no row here on 2026-09-22.
4. **Reports the depth backfill (#43).** `depth_progress()` is the one definition of the figures, and four of them are counter-intuitive enough that the first implementation got each one wrong in a way that read as confident and correct:
   - ***resolved* is `depth_skip + depth_success`, never `depth_total`.** `depth_total` adds `depth_fail`, which carries **transient** failures — not ledgered, re-requested next run. Counting them let a city report `depth complete` with panos that will never have depth (the *ordinary* end-state: the last stragglers are the ones that keep failing) and made the figure run backwards after a heavy-failure night. The cost is a one-night lag on `unavailable` verdicts, which are permanent and ledgered but sit inside `depth_fail`; they land as skips on the next run. A converging lower bound can delay "complete", never assert it falsely.
   - **Every rate is per CALENDAR night**, reindexed over the last `DEPTH_RATE_NIGHTS` dates with missing nights counted as 0, and **both rates divide by the same span** — the nights the log covers, capped at the window. Requests over 7 and panos over the span printed a two-night-old city as `+590 panos/night on +169 requests`. A city only gets a slot on the nights the window reaches it and writes no row otherwise, so averaging the dates that happen to appear read three runs spread over a month as three consecutive nights — 10× optimistic, and biased against exactly the starved cities the fleet block exists to surface. Same reasoning for `quiet_nights`, which is calendar nights since the last request rather than a count of quiet rows.
   - **The ETA divides panos by panos**, not panos by requests: a night of heavy transient failure spends requests and resolves nothing.
   - **A corpus of 0 is refused** (`corpus_size`). `depth_eligible` is `len(gsv_panos)`, so an empty pano-list answer writes a plausible `0`, and `last_value` skips blanks but not zeros — one such night erased the city from the stats line, the fleet block and the `longest remaining` ranking. Only `0` is refused: a corpus legitimately **shrinks** as Google retires panos, even below what the ledger holds, so "smaller than resolved" is not evidence of anything.
   - **A request is not progress; a save is (rule 10, #163).** `quiet_nights` counts requests, so a phase whose every request failed reset rule 7 nightly — measured: 10 nights of 25 transient failures and 10 nights of 1,889 requests all written off as `unavailable` both returned no issue, the second with a confident `~39 nights left`. `barren` counts the nights since the last save that **made requests** (`unsaved_request_nights`, distinct dates, not rows), not calendar nights; the stats line prints the same count, and a city with no save in the log says so rather than citing one. The two all-failed shapes are separable only **across two rows** — `unavailable` is ledgered at once and returns as the next run's skip, transient never is — so `unavailable_share` (ledger growth over the failures of every requesting row but the newest) is 1.0 or 0.0 by construction, and `None` until two rows have asked. The ledgering arm is **CRITICAL because it is permanent** (a false `unavailable` is never re-requested; the fix is a ledger scrub, `docs/ops.md`). The **walked-list guard** (`depth_total >= depth_eligible` on the newest requesting row) is what keeps the straggler end state quiet — a few panos failing every night are *reached* every night — and `quiet_nights < DEPTH_STALLED_NIGHTS` hands the night to rule 7 once requests stop, so one outage is never two findings.
   Rule 4 reads `image_minutes` directly **with the median floored** (`LONG_RUN_MIN_MEDIAN`) — a mature city's image phase is a ledger read while depth spends the whole slot, so total-minus-depth was 0 on every row, the median was 0 and `median > 0` switched the rule off entirely; at a median of 1 it warned on an ordinary 4-minute phase. Inside the queue it **cannot see a hang** — a hung image phase is killed at slot + `--kill-grace`, leaving `image_minutes` blank, so only rule 5 sees it, and only at ≥3 of 7; it catches long legitimate phases (a first scrape) and hand runs without `--max-runtime` (#163). Rule 5 reads `PHASE_COLUMNS` only (field 19 is blank on every older row), rule 6 flags *overlapping* runs rather than same-day ones, rule 7 names the *candidates* for a stalled phase rather than asserting a cause (an unwritable ledger returns `(0, 0, skipped, skipped)`, **not** five zeros, so both arms of the old two-way diagnosis were wrong on the shape they existed to catch), rule 10 flags a phase that requests and saves nothing — counted in nights that **made requests**, not calendar nights, or a `--skip-depth` rollback followed by one bad night fires, and rules 8 and 9 report a corpus or a row width that cannot be believed — and rule 9's rows are **dropped from the frame**, not padded into runs: counted-then-padded let a stray comma turn a 183,680-pano city into `depth 0/12` with rule 8 silent. Rule 9 dates a torn row by its field 1 (written first, so it survives the tear) and **warns only within `MALFORMED_RECENT_DAYS`**; older rows are one INFO line, and a city with only INFO findings prints blue and counts OK (#163 — 20 of 26 warnings one morning were 2022-era tears). An **undatable row counts as recent**: a tear can cut the stamp itself, and that is tonight's row — and *undatable* is anything short of a full `YYYY-MM-DD HH:MM:SS` (`_FULL_STAMP`), because ISO8601 parsing accepts a prefix and dated `2026-09-2` to 2 September. **Rules 2 and 3 group by date** for rule 6's reason, and **rule 3 fires only with evidence of work** (#163) — field 5 growth across the window or field 5 − 11 on the newest row, each at least `ZERO_PROGRESS_MIN_NEW_WORK`, or a blank or `0` field 5 (unknown, so it fires as before: field 5 is `len(image_pano_infos)` with no empty-list guard, so `0` is what an empty pano-list answer writes, `corpus_size`'s reason in field 19); not field 11 alone, which counts attempts and so does not grow when the image phase is starved. A steady nightly set of *transient* image failures goes unreported by every rule once it is a week old (at onset rule 2 flags a set of ≥140 for up to 7 nights, as "permanent" failures) — **a trade the gate makes, not a pre-existing gap**: the ungated rule 3 caught it after 30 nights, and the gate cannot tell it from a mature city with nothing new (`docs/log-analyzer.md`, "What `log.csv` cannot show").

**check_cvmetadata_schema.py** (#135) — asks a LIVE deployment which fields `/adminapi/labels/cvMetadata` serves and compares them against what `CropRunner` requires. Same extracted shape as the runners (`build_parser()` / `configure_logging()` / `main(argv=None)` behind a `__main__` guard), so importing it is inert and its tests drive `main()` against a stubbed transport. It exists because `label_type_id` became `label_type` upstream (SidewalkWebpage#4103, 2026-09-02), the cropper produced zero crops against every deployment for 16 days, and CI was green for all of them — the suite is network-free by design, so every `-d` test runs against a fixture this repo wrote and a fixture cannot notice the server disagreeing with it.

1. **It lives outside `tests/`, and that is the point, not a compromise.** The network-free suite is a property worth keeping; a contract with another codebase simply cannot be checked inside it. Exit codes are the unattended interface (0 ok, 1 a required field is gone, 3 the deployment could not be read — a check that did not run has not passed), so a crontab line mails the failure the way `log_analyzer` does.
2. **The required list is read off `CropRunner` at call time** — `required_fields()` returns `REQUIRED_LABEL_COLUMNS`, `required_field_groups()` returns `LABEL_TYPE_COLUMNS` as one either/or group. Never restated: two copies of a field list drift silently, which is the bug. `TestTheFieldListComesFromCropRunner` moves the constants and asserts the verdict moves, so a copied tuple fails rather than passing every other test in the file.
3. **A field the server ADDS is never a failure**, only `not_required` on the report. Servers add fields; a check that cried wolf gets muted, and a muted tripwire is worse than none. `Comparison.ok` deliberately does not consult `not_required`.
4. **Only the first record is read.** cvMetadata is the city's whole label list (183,682 rows for seattle-wa), so the body is streamed and the read stops at the first complete record, whose keys *are* the field names — bounded by `MAX_PREFIX_BYTES` for a server that never completes one. A check costing more than the thing it guards does not survive contact with a monthly bill.
5. **Only a JSON array whose first element is an object counts** (the #99 positive-evidence rule). An error envelope, a proxy's login page, a truncated body and an empty list are each `SchemaUnavailable` → exit 3, never "zero fields served" → every required field named as missing. "The endpoint moved" and "we never reached the endpoint" are two different people's problem.
6. **No default host** (`--host`, else `$PS_CVMETADATA_HOST`, else exit) — `resolve_sftp`'s and `--cities`' rule. The schema is the app's, not the city's, so one deployment answers for the fleet. Fields with a documented fallback (`pano_width`/`pano_height`, which `_metadata_dims` degrades past) are deliberately NOT checked: they have no constant in `CropRunner`, so checking them would mean writing the second field list this whole thing exists to prevent.

**migrate_depth_artifacts.py** — offline, idempotent one-off that rewrites pre-v2 (x-mirrored, unversioned) depth artifacts into v2 column order. The scraper never revisits an existing artifact, so a store scraped before #58 keeps mirrored artifacts forever without this.

**migrate_crop_store.py** (#159) — offline, idempotent, resumable one-off that moves a pre-#159 flat crop store (`<crop-dir>/<label_type_id>/<label_id>.jpg` plus its store files at the root) under `<crop-dir>/<city>/`. Same #52.1 shape (`build_parser()` / `main(argv=None)` / `migrate_store(crop_dir, city, dry_run=False)`), and it imports `CropRunner` (side-effect free) for `city_id`, `_is_numeric_name`, `_is_label_type_shard`, `city_named_directory`, the store-file names, `refuse_production_crop_store` and `check_store_city` rather than restating any of them. Load-bearing: **it moves and never replaces** — `os.rename` after an `os.path.lexists` check, never `os.replace`, `shutil` or `unlink`, and a shard is `rmdir`'d only once empty — so every file ends up either in its place or where it was, and a test compares the multiset of file bytes before and after. A shard moves whole when its destination does not exist (one syscall over sshfs), else file by file; **store files move after the shards and `crop_rule.json` last**, so a run killed partway leaves the root marked as a flat store — CropRunner keeps refusing it, and the next migrator run re-checks the city. It refuses (exit 3, nothing touched) a root already named for `--city` (`CropRunner.city_named_directory`), a production-shaped root and a root or `<city>/` marker naming another city or unreadable. **It cannot tell one city's crop from another's** — it files every crop under `--city` and says so on both channels whenever it moves anything — so a flat store more than one city was cut into must never be given to it (`docs/cropper.md` says what to do instead); do not let a message or a doc offer it as the remedy for one. Only `_is_label_type_shard` directories move: any other all-digit directory, a shard that is itself a symlink and, when a shard moves file by file, a symlink or directory inside it, is left and counted (a shard that moves whole is one `os.rename`, carrying whatever is inside it; nothing here writes links). A failed listing or `rmdir` is a counted `FAILED`, like a failed rename; only an unlistable root stops the run, with a message and exit 1. It has **no `.jpg` predicate** (it moves every file in a shard, `.part` included), which keeps `tests/test_downscaled_sidecar.py`'s `JPG_PREDICATE` offender list unchanged. Exit 1 on any collision, left directory or symlink, or failure, predicted ones included under `--dry-run`, because the root stays refused until a person settles each; the consumers' re-point reminder prints only when something moved or would.

**downscale_panos.py** (#115) — offline, idempotent, resumable sweep writing `<pano_id>.w8192.jpg` beside every pano wider than the viewer's cap, via `downloaders.common.write_downscaled_sidecar*`. Judges each pano from two JPEG headers (its own and its sidecar's), so a finished store decodes nothing; `--max-runtime` leaves the rest counted as `unreached`. `--min-width PX` (#160) writes copies only for panos wider than `PX` — `16384` is the #121 width tripwire's remedy, the frames the viewer fleet cannot render, instead of the fleet-wide +63% — and counts the rest over the cap as `under_min` **before** reading their sidecar, so a filtered copy is never reported `current`. `scanned == written + narrow + current + failed + under_min` on every path (`unreached` sits outside), a floor at or below `--max-width` is an argparse error because it would filter nothing, and the summary line always carries the `under --min-width` clause.

**The whole feature is switched off (2026-09-09) and this is the only writer that CREATES a copy.** `downloaders.common.WRITE_DISPLAY_COPIES = False`, so neither downloader writes one; this script is unaffected, because it runs only when a person runs it, and `refetch_panos._refresh_display_copy` still rewrites a copy **already on the store** after a swap (item 7 below) but never creates one. #115's premise was wrong by 2×: Pannellum uploads an equirectangular image as **two half-width textures**, so its ceiling is `2 × MAX_TEXTURE_SIZE` and a device advertising 8192 renders the 16384-wide frames the store holds. Measured demand: 140,599 wide expired panos viewed **29 times in ninety days** against a 6.4 TB backfill, and ~50 users a year who genuinely cannot render 16384. The web app cuts the copy on demand instead (SidewalkWebpage#5256, ~105 MB heap and ~2.0 s inside the JPEG decode), which also retires the "ImageIO can't do this without OOM-killing the JVM" half of the rationale (#5239). **Kept rather than reverted because the margin is exactly zero** — `16384 = 2 × 8192`, GSV has already widened once (13312 → 16384), and this repo is the only place that sees the reported width change. Full reasoning and the numbers: `docs/ops.md`.

Five things about it are load-bearing:
1. **`sidecar_is_current` compares BOTH dimensions against `downscaled_size(pano_dims)`, not just the width against the cap.** The name already promises the width, so checking only that proves the file is not truncated and says nothing about *which* pano the copy belongs to: a 1024×999 sidecar beside a 2048×1024 pano read as current, and so did any sidecar written under an older aspect rule. The height costs nothing — `jpeg_dimensions` already returned it.
2. **It is a repair pass, not a one-off.** `download_single_pano` returns `skipped` at its `exists()` check *before* the sidecar code, so a copy that failed to write tonight is never retried by the scraper. A `display copy not written` line in `scrape.log` is cleared only by running this again.
3. **A display copy is ~63% of the native file, not a thumbnail** — measured 3.82 MB against 6.08 MB on `samples/sample_pano.jpg` at `DOWNSCALED_JPEG_QUALITY` 85 (2.82 MB, 46%, at 75). Sweeping fleet-wide is close to a **+63%** commitment on the whole store; `--dry-run` gives the count to multiply. (It read ~60% until the 2026-09-09 review: 3.82/6.08 is 62.8%, and the store figure was a restatement of the per-file one, so both moved.)
4. **Never fatal in the downloaders**: a failed sidecar is logged and the native pano stays a success, because the native file is already the resume marker. With the switch off this and item 2 both describe a path nothing takes — they govern the downloaders only while it is on. The rule still binds `refetch_panos`, where a failed rewrite would NOT be sweep-repairable, which is why it deletes the copy instead (item 7).
5. **The guard is at the automatic callers, not in the primitives — and that is a rule, not a snapshot.** `gsv._write_display_copy`, `mapillary._write_display_copy` and `refetch_panos._refresh_display_copy` each read `WRITE_DISPLAY_COPIES`; `write_downscaled_sidecar*` never do. Pushing it down into them is the "simplification" that leaves every store-clean assertion green while silently disarming this script. `TestTheSwitch` fails on exactly that, pins the shipped default to `False` so a flip cannot be accidental, and — because those two only cover the writers that exist today — asserts that **every** production module calling a primitive reads the switch, exempting only `common.py` (which defines them) and this script. `110-panoramax-source` carries an unguarded fourth caller, so whichever of it and #120 lands second must bring the guard with it; that assertion is what says so.

**The width tripwire (#121) watches the zero margin that keeps this script** — it lives in the downloaders, not here. `common.warn_if_wider_than_viewer_ceiling` warns on both channels when a source reports a frame wider than `common.VIEWER_MAX_PANO_WIDTH` (16384 = 2 × 8192) — GSV in `resolve_frame` before any request (not in the `resolve_zoom_and_dims` wrapper, which only refetch calls since #74), Mapillary and Panoramax from the stored JPEG's header after the rename. Never a gate, never a caller of the sidecar primitives, no once-per-run latch (each line carries the whole message, because the alarm wrapper cuts the middle of a long night; its remedy is a pointer to `docs/ops.md`'s "The width tripwire" and "verify, then budget the disk before any sweep", never the switch-and-sweep steps themselves, since those are a fleet-wide +63%). The ceiling is a literal, **not** `2 * DOWNSCALED_MAX_WIDTH` — the cap is a disk choice, the ceiling a device fact — and a test pins that. **Not a `log.csv` column and so not an analyzer rule**, deliberately: #121 says a persisted width must be proposed first. **It alarms once per host, then only warns (decided on #153, 2026-09-26).** The per-pano warning never changes an exit code; instead every firing bumps `common.ceiling_sightings()`, and `DownloadRunner.main()` reads the *difference* across its own run (the count is process-wide and never reset, so a wide frame seen earlier in the process is not tonight's). If it went up, `common.arm_width_alarm(path)` creates the latch exclusively — `sidewalk-width-ceiling-alarmed` in the temp dir or `--width-alarm-latch`, local disk for the depth latch's reason — and **only the run that creates it exits 1**, so `--only-on-failure` delivers one alarm and the city does not stay red every night after (Google does not un-widen, and a permanent red hides real failures). An unwritable latch resolves towards alarming, every run. `refetch_panos` shares the tripwire but never arms the latch. Don't make it fail every sighting, and don't move the latch onto the store: per-city, it would alarm up to 53 times for one event.

**refetch_panos.py** — offline, idempotent one-off that re-fetches panos downloaded while the CBK URL carried `fover` (#73), recovering the polar-band resolution it cost. Same problem shape as the depth migrator — the scraper short-circuits on file existence, so nothing on the store is ever revisited — but with an inverted risk: the depth migrator rewrites an artifact it can fully reconstruct, while this one **replaces imagery that may be irreplaceable**, since ~52% of labelled panos no longer exist at Google. **The `fover` pass itself does not run** (decided 2026-09-05, `reports/2026-09-05-fover-refetch-pilot.md`): the 512-px polar bodies CBK serves without `fover` are server-side upscales of the 256-px ones, so there was never resolution to recover, and a quarter of the panos Google still serves have been re-rendered since scrape. The tool stays as a general, tested repair pass.
1. Work-list in, from `reports/scripts/pano_y_histogram.py --write-worklist` (panos with a label in a half-res band, ~7.5% of Seattle's labelled panos) or `--from-store`. Read with `csv`+`gzip`, never pandas — same #46 reasoning as `progress_check`.
2. `decide_without_fetching()` resolves `absent`/`unreadable`/`not_affected`/`already_clean`/`dims_changed` from the store alone, at **zero requests**, on every run — none of the five is ledgered. That is what makes a pass affordable, makes a re-run after a finished sweep free even if the ledger is lost (a repaired file's mtime is past `--fixed-after`), and means a wrong `--fixed-after` or a later `--allow-dims-change` can be corrected by re-running rather than by scrubbing rows. The `already_clean` gate is mtime-only, so it is load-bearing: a copy that reset mtimes makes every pano `already_clean`.
3. `refetch_pano()` fetches through the `gsv.resolve_zoom_and_dims` / `gsv.fetch_pano_image` seams (the first is the probe alone, never photometa — see the `gsv.py` bullet), then refuses to swap on **`frame_grew`** (Google now serves the pano larger, so this grid would return the top-left corner of it — checked by `gsv.frame_covers_pano` *before* the fan-out), **`upscaled`** (a fallback zoom would be a 4× downgrade), **`undersized`** (nothing gained), or **`too_black`**. The swap goes through `atomic_output_path`; every other path leaves the stored bytes byte-for-byte untouched, and a test asserts that on the bytes rather than on the return value.
4. `refetch_log.csv` remembers the request-spending outcomes (`LEDGERED_OUTCOMES`) with the ledger semantics the two nightly ledgers use — a row is permanent, transient failures are unledgered and retry. **`undersized` is the exception:** it is #73's tripwire (the request is costing resolution again), so it is never ledgered, three in a row stop the run, and any at all exits 1. It writes **nothing** to `pano_id_log.csv`, `depth_log.csv`, `log.csv`, or any `.depth.npz`, and a test asserts that too. Candidates are **shuffled**, deliberately discarding the work-list's order: with the breaker, a stable order would let five persistently failing panos at the head stall every run.
5. `--measure` writes per-pano recovery to `refetch_measurements.jsonl`, one line per swap as it lands (not at the end of the run, and never for a swap whose save failed): bottom-band MAE old-vs-new, that band's own halve-and-restore cost, and the **horizon band as a control** — CBK served those rows at full size in both eras, so their MAE is our own JPEG round-trip and the difference is the recovered detail.
6. **Replacing a pano does not refresh crops already cut from it** — existing crops are the cropper's resume marker. The `replaced` rows in the ledger are the list of panos whose crops need deleting and re-cutting.
7. **It DOES refresh the #115 display copy** (`_refresh_display_copy`), and must — **never creating one, always refreshing an existing one.** Every gate above refuses a swap that changes the frame, so a stale sidecar would keep the width its name promises and read as `current` to `downscale_panos`' sweep for ever — the viewer serving a copy of precisely the imagery the pass replaced, with nothing on disk able to tell. Unlike a crop, the sidecar is a pure function of the pano and the raster is in hand at the swap. This is the one place `WRITE_DISPLAY_COPIES` does not fully turn off, deliberately: the switch says stop making a new artifact, not start lying in the one already on the store. Never fatal, for a sharper reason than in the downloaders: the swap has **already landed**, so raising would leave the pano unledgered and the next run would spend another ~512 tile requests redoing it. **So a failed rewrite DELETES the copy (#122)** — the one file this tool ever deletes. Left in place it would not be sweep-repairable: the write is atomic, so a failure leaves the *old* copy intact, `sidecar_is_current` judges from dimensions alone and every gate above refuses a frame change, so the stale copy has exactly the expected dims and reads as `current` for ever. A *missing* copy is repaired by the next `downscale_panos.py` sweep, **whenever one is run** — nothing schedules it — and until then the web app serves the native file. That does not break the no-destroy rule, which is about panoramas: a display copy is a derivative of the panorama that just landed. The delete is gated as narrowly as the write: only on this path, which runs only after `replaced` (the refusal battery in `tests/test_refetch_panos.py` asserts the copy survives every refusal byte for byte), and only the exact `downscaled_sidecar_path` for the current cap. Never fatal either; a successful delete is logged to `refetch.log` only, at WARNING (a correct state the next sweep repairs, not an error), while a delete that itself fails goes to stdout too, at ERROR, naming the file, because that is the one case where a person must `rm` it and re-run the sweep.

## Storage layout

Everything lives under the storage root, with two-char pano-id prefix sharding:

| Path | What |
|------|------|
| `<pano_id[:2]>/<pano_id>.jpg` | Stitched panorama |
| `<pano_id[:2]>/<pano_id>.depth.npz` | Depth artifact (see below) |
| `<pano_id[:2]>/<pano_id>.w8192.jpg` | Display copy of a pano wider than 8192 px (#115). **Not written automatically since 2026-09-09** — only by `downscale_panos.py`, plus `refetch_panos` refreshing one that already exists, and deleting it if that refresh fails (#122). Copies written before the switch are still on the store, so: **never list the store's `*.jpg` by hand — call `downloaders.common.walk_store_panos()`**, the one definition of "this file is a panorama"; a walker that forgets `is_downscaled_sidecar()` does not fail, it invents pano ids like `<real id>.w8192` |
| `pano_id_log.csv` | Per-pano image ledger: `pano_id,downloaded,fetched_at`; two-field rows predate #129 (committed 2026-09-10, on the production store from 2026-09-17) and are never backfilled, and a `skipped` verdict (file already on disk, source never contacted) writes a **blank** stamp rather than laundering an unknown fetch time into today's - blank and absent both mean unknown. `progress_check` accepts **both** widths - a bare `len(row) != 2` silently parses a timestamped ledger as EMPTY. The stamp is last so the verdict stays in column 2; an end-anchored `grep ',0$'` no longer matches a `0` row |
| `depth_log.csv` | Per-pano depth ledger: `pano_id,saved\|unavailable` |
| `log.csv` | One 19-column row per run |
| `scrape.log` | Rotating run log (10 MB × 3) |

At the store **root** (the queue's `--store-root`, one level above the per-city storage roots): `scrape_queue.log`, and **`.pano-store`**, the store marker the operator creates once on the remote store (#161). The queue refuses to run without it.

**The store is an archive, not a cache — `docs/ops.md` → "The store is an archive, not a cache" is the rule, and it binds any code that writes a `.jpg`.** ~52% of labelled panos are already retired at Google and ~24% of the survivors come back re-rendered (#114), so a stored pano is usually the only copy of *that picture* that will ever exist and replacing one is a deletion, not a refresh. Two tiers: **the download path never overwrites** (all three downloaders short-circuit on `os.path.isfile` — that check is also the resume marker, which is exactly why a future writer that resumes differently would inherit no protection), and **a repair path overwrites only on positive proof the replacement is strictly better** (`refetch_panos.py`'s four gates). The uncovered case is a re-render at **identical dimensions** — `dims_changed` catches only the ones that changed frame, and nothing downstream can see the rest. The gate that would close it (horizon-band MAE against the stored file, zero extra requests, 45.6× separation) is deliberately **not built**, because no writer runs; the rule is what stops the next one shipping without it.

**`pano_id_log.csv` gates the image phase** — ids already in it are skipped on later runs. Note the caveat in `docs/ops.md`: a permanent verdict is ledgered and never retried, while a transient failure leaves no row.

**`depth_log.csv` gates the depth phase**, but only for permanent outcomes: `saved` and `unavailable` are ledgered and never retried; transient errors (including storage failures) are counted but **not** ledgered, so they retry next run. The artifact on disk is ground truth — deleting the ledger just makes the next run re-stat artifacts and re-request unresolved panos.

## Config

`config.py` holds `thread_count` (image-phase tile fan-out, default 8), a rotating `headers_list` (randomly picked per request), `proxies` (set to the `http://`/`https://` sentinels to disable), and the three depth pacing settings.

**Depth pacing is adaptive, and `depth_min_request_interval` is a floor rather than a rate (#43).** A run opens at `depth_start_interval` (1.0 s), doubles on any push-back up to `depth_max_request_interval` (30 s), and decays ×0.8 back towards the floor only after 200 consecutive clean requests; the gap slept is drawn `uniform(interval, 2 × interval)`, so there is no cadence to fingerprint. Three things follow that are easy to get wrong:
- **The floor bounds how aggressive this host can ever get** — nothing draws a shorter gap. The 0.25 s default is the pace the 2026-08-09 photometa census ran 1,360 requests at with zero push-back, i.e. the fastest rate we have live evidence for. It is deliberately *not* 0, and the old advice to leave it at 0 "because the backfill is a multi-month job" was wrong on both halves: a photometa request measures 0.077 s median from the production box.
- **Push-back is detected via urllib3's retry history, not the status code.** Retries happen inside the adapter, so a 429 never reaches a response hook and an exhausted policy raises `RetryError`. What is observable is that a response *needed* retries — the earliest available warning.
- **A floor of 0 disables the throttle, not the reaction:** a push-back still lands on `DEPTH_PACE_MIN_BACKOFF` (1 s), because doubling 0 stays 0.
- **Earned speed persists across runs; back-offs do not.** Every city run is its own process, and measured over the first three production nights every one opened at 1.0 s and ended its 12-minute slot still ramping (1,400 clean requests to the floor, a median of 585.5 per slot at 1.23 s — `reports/2026-09-09-depth-backfill-first-nights.md`, which lands with #126), so the fleet's real rate was the opening interval and the five longest cities were 240–463 nights out. The interval and clean streak a run *earns* are now written to local disk beside the **default** block latch (`--depth-pace-state`, `gsv.default_pace_state_path`; `--depth-block-latch` moves the latch and **not** this file, so a host that needs both off `/tmp` passes both flags) and the next run opens there, clamped into `[floor, depth_start_interval]`. A file older than 24 h, unparseable, non-numeric or `NaN` opens careful (`json.loads` accepts a bare `NaN`, and a NaN interval passes every clamp and reads as "no gap"); `_load_pace_state` catches `Exception`, not a list of types, because the path is a fixed name in a world-writable temp dir and a `RecursionError` out of `json.load` would otherwise end the depth phase for every city, every night. The write happens inside a `requests` response hook, so it never raises. What the pacer cannot fix is the slot: the queue spends 12 minutes per city whether or not the city has work.
- **Only Google forfeits the standing — the same rule the latch follows, not a second convention.** The bullet below says *only a blocked stop latches; the breaker counts storage failures, and a full disk is not Google*. `on_pushback` is fed by the phase's network arm (a DNS blip, one connection reset, a non-JSON body) and by its unexpected arm, which catches the `DepthPayloadError` raised for a pano carrying depth but no planes — a property of **one pano's upstream payload**. Each of those must slow *this* run down and leave the host's file alone: candidates are shuffled, so one malformed pano in 1.43 M is met at random, and forfeiting there would hand the next 51 cities a 1.0 s opening interval, seven decay steps (~2.4 slots) to earn back. `on_pushback(..., from_google=True)` — set only by `_pushback_hook`, on a push-back status or a retry history that **holds** one — and a `DEPTH_STOP_BLOCKED` stop are the only things that forfeit it. `Retry.history` records every retry cause, and a connect or read retry (a DNS lookup that failed and then succeeded, one reset, a read timeout) carries `status=None` and the error: that is this box's evidence, so it backs *this* run off and forfeits nothing (`_retry_history_is_googles`) — the same blip exhausting all five retries already lands in the network arm as local, and the blip that cleared must not cost more than the one that did not.
- **What is persisted is `_earned`, never `interval`, and the streak rides with the interval it was earned at.** They are different numbers: a local back-off widens the live gap without touching the standing (writing `min(interval, start)` would be the forfeit by another route, one seam later, at the end-of-phase `save()`), and the decay steps that walk it back are re-earning ground already held, so `_earned` only ever moves down. The decay rule is 200 clean requests *at the current interval*, so `_persist` writes the streak only when `interval == the value being written` — otherwise 190 observations Google gave at 2 s spacing would justify a speed-up at 1 s.
- **Zero requests is zero evidence, and one process at a time spends the standing.** A phase that made no requests (a Mapillary-only city, a fully-backfilled one, a run whose image phase already spent `--max-runtime`) writes **nothing**, not even a fresh timestamp — `download_depth_maps` is called unconditionally for all 52 cities, so restamping would keep refreshing a freshness window that then never expires. The end-of-phase write is an `ExitStack` callback (`remember_standing`), not a statement after the loop: decay steps persist as they are earned, but the streak in progress is written only there, and `DownloadRunner` translates SIGTERM into `SystemExit(143)` precisely so that exits like it run under the queue's `--kill-grace` backstop or an operator's stop. And the phase holds an advisory lock (`<state path>.lock`, `common.exclusive_host_lock`) for its whole duration: `scrape_queue`'s lock guards the *queue*, not this host's depth rate, and a manual backfill alongside the nightly window is a documented workflow. A phase that cannot take the lock does all its work but neither inherits nor persists — the pre-#43 behaviour — and warns on stdout. `scrape_queue.py` keeps its own copy of the `flock`/`msvcrt` idiom deliberately; collapsing them would make the fleet driver import the image package for four lines.

**A refusal is remembered across runs.** A `DEPTH_STOP_BLOCKED` stop writes a timestamp latch (default: system temp dir, `--depth-block-latch` overrides) and any depth phase starting within `DEPTH_BLOCK_LATCH_HOURS` (6) skips itself at **zero requests**. It is on local disk, not the store, because the storage dir a run gets belongs to one city and because what is remembered is this host's standing with Google. Only Google's refusal latches — a depth blocked stop, the image phase's push-back breaker (#162), or a photometa refusal in the image phase (#74), the last two both through `gsv.record_google_refusal`, which also forfeits the earned pace and returns whether the latch landed, and both of whose WARNINGs are worded from that return; the depth breaker counts storage failures, and a full disk is not Google. The image phase reads the latch only as **probation** (`GSV_PUSHBACK_PROBATION` = 1 refused pano instead of 3 while it is fresh, `gsv.fresh_block_latch_hours`), never as a stand-down: the depth phase latches after one photometa refusal, and standing images down on read would let one interstitial stop the whole fleet's images for 6 h. Every ambiguous latch (missing, unparseable, implausibly future-dated) resolves towards scraping. **The image phase shares the latch file, not the pacer (#74):** its per-new-pano photometa request is skipped while the latch is fresh, and a refusal met there writes it (warning once, on both channels) so the depth phase later that run stands down, and forfeits the pacer's earned standing as a depth-phase refusal does (review decision D6). **A photometa refusal is drawn on the push-back breaker's line** — `isinstance(e, DepthBlockedError) or gsv.pushback_reason(e) is not None` — so a 5xx storm exhausting the photometa session's retry policy (forcelist `[429, 500, 502, 503, 504]`) is an ordinary photometa failure, counted towards `PHOTOMETA_MAX_CONSECUTIVE_FAILURES`, and never latches; before #172's final review it latched the fleet for 6 h on any `RetryError`. (The depth phase's own `except (DepthBlockedError, RetryError)` is still that broad, a known follow-up.) **One latch path and one pace path per run:** `gsv.image_host_state_paths` is the one resolution order (explicit, then `gsv.image_block_latch_path` / `image_pace_state_path`, which `DownloadRunner.run` sets from `--depth-block-latch` / `--depth-pace-state`, then the host default), and `download_panorama_images` resolves its breaker's pair through it and wraps its loop in `gsv.scoped_image_host_state`, so photometa — which `download_pano` gives no path — writes the same files the breaker reads. `TestTheTwoLatchPlumbingsAgree` passes one pair explicitly and another in the module and asserts the refusal lands on the explicit one. **A refusal and a stand-down are two run conditions, not one (#161)** — `depth-refused` (this run was refused and wrote the latch) and `depth-stood-down` (a live latch at phase start) both record `depth_stop='blocked'`, and both fail the night; the stand-down alarms even when nothing was refused tonight, because the latch outlives the window. `depth-breaker`, `depth-ledger-unusable` and `depth-unavailable` (streetlevel not importable — which now prints a `WARNING` line as well as logging, it was logging-only) are the phase's other three (`gsv.DEPTH_CONDITIONS`). The scattered-errors arm is deliberately **not** a condition. An image-phase photometa refusal (#74) or push-back trip (#162) writes the latch, so it reaches the queue as that run's `depth-stood-down` when its depth phase then runs; the push-back trip also puts `gsv` in the tripped set, so the city exits 1 and is booked `failed`, not `ok`.

All three host-level defaults — the floor, the latch path and the pace-state path — are neutralised suite-wide by `tests/conftest.py`'s `_isolate_depth_host_state`: without it the pacer's real floor makes every depth test sleep, one blocked-stop test writes a latch into the machine's temp dir that stands down every later test's depth phase, and one test's earned speed becomes the next test's opening interval. The same fixture resets the image phase's per-process photometa memory and its two host-state paths (#74), which are module state for the same reason.

## Artifact storage (standing rule)

Every research and engineering artifact — datasets, annotations, measurement files, figures,
scripts, model outputs — lives in **GitHub (this repo or a sibling org repo) or the
`projectsidewalk` Hugging Face org, nothing else**. Personal cloud storage (Google Drive,
Dropbox, ad-hoc shared links) is easy to reach for in the moment but doesn't survive people
moving on: links rot, accounts close, and experiments have had to be re-run because artifacts
that felt accessible at the time were no longer findable later. Version-controlled, org-owned
homes are the only storage that outlives any one person's involvement. The bar: a fresh clone
plus the referenced HF dataset must reproduce every number in `reports/`.

## Things that are easy to get wrong

- **The three file intakes read with `csv`/`json`, and must not go back to pandas (#72).** `pandas` is a
  dev/ops dependency now (`requirements-dev.txt`, for `log_analyzer/` and `reports/scripts/`), and a test
  asserts no production module imports it. The battery in `tests/test_csv_intake.py` was **measured**
  against `pd.read_csv` before the swap, and three of those measurements are the reason it happened: a row
  with **one surplus field** made pandas consume the first column as the frame's index, so every field
  shifted and the real `pano_id` vanished — silently; **`has_labels` had no fixed type** (bool, int64,
  float64, or `str` for junk *and* for `' True '` with padding), and `select_image_panos` is a plain
  truthiness test, so the `str` cases silently defeated `--all-panos`; and **one blank cell retyped a whole
  column**, so a single missing `width` made every other row's width a float and the blank itself a `NaN`
  that `gsv`'s `is not None` guard cannot see. Blank cells become `None` in `DownloadRunner` and stay `''`
  in `CropRunner` — deliberate, and explained at both seams.
- **CropRunner's `--city` roster is `log_analyzer/cities.csv` read as a FILE — never imported, never copied
  (#159).** `--city` names the crop store's directory, so a well-formed typo would start a new store;
  `city_id()` checks the regex, then membership in `known_city_ids(CITIES_FILE)` (active rows only: a
  `#`-commented deployment has no panos to crop), read at parse time. Importing `log_analyzer` would pull
  pandas into a production module (`tests/test_csv_intake.py` fails on that), and a constant list here would
  drift from the roster `docs/ops.md`'s "Adding a city" keeps. An unreadable roster fails **closed** (exit 2
  naming it): accepting every well-formed name there is exactly the gap. Semantics tests monkeypatch
  `CITIES_FILE`; only `TestTheCommittedRosterIsSafeAsDirectoryNames` reads the real list.
- **`print` and `logging` are two channels with different jobs — do not "unify" them.** `print` is the
  operator-facing run narrative and the warnings **the night's message carries** (cron's mail rule, delivered by `cron_notify.py` on the production host, #141); `logging` is the durable per-item detail in
  `scrape.log` / `crop.log`. **A warning that matters goes to both**, which is the depth phase's pattern
  (`logging.error(...)` then `print(...)`), because stdout is how someone hears about it tonight and the log
  is what is still there next week. #52 item 6 read the mixture as inconsistency; it is mostly deliberate,
  `docs/downloader.md` leans on a `WARNING` reaching the night's message, and ~15 tests assert on `capsys`. A print-to-logging sweep
  would break all three. The one real violation — `filter_supported_sources` warning on stdout only — is
  fixed; `caplog` assertions now sit beside its `capsys` ones so a revert fails. **A warning that should
  fail the night also goes into the run summary as a condition** (#161, `note_condition`): stdout reaches
  the message only on a night that already exits nonzero, because production delivers with `--only-on-failure`.
- **`log.csv` column 1 is a wall-clock stamp WITH its offset; every duration is `time.monotonic()`. Don't merge the two clocks (#101).** It was `str(datetime.now())` — a bare local reading, harmless only while every scraper host ran UTC, which is the assumption pinning the schedule to `America/Los_Angeles` removes. `log_analyzer` compares it against `datetime.now(timezone.utc)`, so a bare row on a non-UTC host is silently 7–8 h out, and `.days` floors, so that moves a city across the staleness threshold in *both* directions. `read_log` parses `format="ISO8601", utc=True`, which is also what lets one file hold both eras — without `utc=True` a mixed column comes back as object dtype and `analyze_city` dies on `.dt`, ending the report for every city after it. Symmetrically, the phase durations were wall-clock differences: the Pacific night window contains 02:00 local, so twice a year every city would report a run an hour longer than it was, and rule 4 warns at 3× the median.
- **The Mapillary token rides in an `Authorization` header, never `params`.** `params={'access_token': ...}`
  is what Mapillary's own docs and every LLM completion suggest, and it's silently wrong: `requests` puts
  the full URL into an `HTTPError`'s message, and `DownloadRunner.py:376` logs `str(e)` for every failed
  pano straight into `scrape.log` — which lives on the SHARED pano store. Not hypothetical: a production
  city's `scrape.log` held a live token in cleartext after a night of Mapillary 400s (#100).
  `downloaders/mapillary.py`'s `TokenRedactionFilter`, wired into `DownloadRunner.configure_logging`, is a
  backstop for *this* secret specifically — it isn't a substitute for keeping every secret out of a URL in
  the first place, since a filter can only scrub a value it already knows to look for.
- **`log.csv` is positional and headerless.** 19 comma-separated fields, blank-padded. Fields 2–6 are an XML-metadata stub kept at fixed values purely so column positions never shift (that endpoint died in 2022). Blank ≠ 0: blank means the phase never finished. Field 19 (`DEPTH_ELIGIBLE_FIELD`) is the GSV corpus size, written from the `finally` because it is known before any phase runs — so it is present on a crashed run and blank only on the crash-before-the-pano-list path and on rows written before #124 deployed. The full table is in `docs/ops.md`; `LOG_CSV_FIELD_COUNT` and `log_analyzer/analyze.py`'s `LOG_COLUMNS` must move together, and a test asserts they do. **Field 11 is not the image corpus; field 5 is** (#163): `image_total` is prior + tonight's attempts, `xml_total` is `len(image_pano_infos)`, and only the second grows when the image phase is starved.
- **`refetch_panos.py` can destroy imagery Google no longer has, so its refusals are the feature.** ~52% of labelled panos are already retired at Google, so the file on disk is often the only copy that will ever exist. Four gates stand between a fetch and a swap — `frame_grew` (the store is a scrape-time archive and Google re-serves panos larger, so a grid sized from a stored 13312x6656 file returns the top-left 81% of a 16384x8192 pano *at the stored file's exact dimensions*, with no undersized tile and no black — the only silent-corruption path in the tool, and `gsv.frame_covers_pano` probes two tiles past the grid edge to rule it out before spending 512 requests — the x probe on the grid's *middle* row, because the probe reads exact-zero luma as "out of range" and the zenith row is the one place a real tile can be uniformly black), `upscaled` (a fallback-zoom stitch would be a 4x downgrade at the same reported dims, and nothing in either image can tell them apart afterwards), `undersized` (a tile still came back at 256, so there is nothing to gain — and the request is broken, so it trips a breaker rather than being ledgered), and `too_black` (a reported frame larger than what Google serves fills the out-of-range tiles with black, which at 13312-in-16384 is 34% and sails under the stitcher's own 50% limit). Adding a fifth means adding it to `OUTCOMES`, deciding whether it belongs in `LEDGERED_OUTCOMES`, and adding it to the byte-for-byte "original survives" test; the mutation battery in `tests/test_refetch_panos.py` exists because a gate that returns the right word after already overwriting the file is the one failure this tool cannot have.
- **Store mode (`--from-store`) never writes `downloaded=0` and never contacts Google (#30).** The `-` prefix on every `get` and the *un*prefixed `cd` are both load-bearing: one keeps an absent pano from aborting the batch, the other makes a wrong city id fail the session instead of reading as 100% absent. The JPEG verifier checks for an EOI as well as the header, because a half transfer keeps a readable header. It accepts up to `TRAILING_BYTES_WINDOW` (64 KB) after the EOI **only if that EOI lies past the main image's first SOS** — a mid-scan cut cannot contain FF D9 (byte stuffing), but an EXIF thumbnail's EOI sits before the scan, inside APP1, and on a small file inside the window; `_first_scan_offset` walks segments by length so it steps over the thumbnail. Dropping the scan-start bound is the "simplification" that lets a truncated file with a thumbnail through. The `PS_SFTP_*` names are copied from `log_analyzer/analyze.py::resolve_sftp`, and `tests/test_store_sftp.py` holds the copies equal.
- **The image loop's breaker is keyed on the SOURCE, not on a verdict, and that is a measurement (#113).** `MAX_CONSECUTIVE_PERMANENT_FAILURES = {'mapillary': 3, 'panoramax': 3}` stops a run ledgering a source after three consecutive `downloaded=0` verdicts, leaves its remaining panos unattempted, withholds the tripping verdict (so a trip costs two false rows, not three), and exits nonzero — which `scrape_queue.py` books as a failed city. **Do not make it source-blind and do not add `gsv` to the table.** A source with no entry is **unlimited**, so adding an imagery source means deciding its threshold or knowingly leaving it without a backstop. Panoramax took its entry with its first city (#110) and needs it more than Mapillary does: three verdict shapes found one instead of Mapillary's one, and two of them — an affirmed non-360 fov and a missing `hd` asset — are wholesale failures wearing a per-pano face, held off the corpus only by a filter in the app that this scraper cannot verify. Measured over the production ledgers 2026-09-06: richmond-va, the only Mapillary city, is **0 permanent verdicts in 9,229 rows** (whole corpus, after the 2026-09-05 catch-up), while seattle-wa is 14,603/183,682 and chicago-il 22,985/272,755 — **7.9–8.4%**, because a retired GSV pano is a permanent verdict and an ordinary one. At that rate three in a row arrives every ~1,700 panos, so a source-blind breaker stops a healthy city that often — most nights during a backfill, less for a mature one. Two tests hold the keying apart and they catch different mutants: `test_a_long_run_of_gsv_verdicts_is_still_ledgered` catches a breaker that *trips* source-blind, and `test_another_sources_verdicts_neither_count_nor_reset` catches one that merely *counts* source-blind and trips per source — which the first test passes, since `limit is None` suppresses the trip for GSV anyway. **Only a success resets the count**, not a transient failure and not a skip: a raise is no evidence about the source, and since every retired Mapillary image raises on every run forever, letting raises forgive the count made the breaker unable to fire on the very fault it exists for (2026-09-09 review). The separation is 259×, not three orders — rule of three bounds the Mapillary rate at 3/9,229 = 0.0325%. The threshold is 3 for `MAX_CONSECUTIVE_UNDERSIZED`'s reason, and the tripped set rides out of `download_panorama_images` as an **out-parameter** rather than a sixth return value, because that tuple is `log.csv` fields 7–11 and `log_analyzer` reads them positionally. **GSV has a second, different breaker for Google refusing the host (#162)** — `GSV_MAX_CONSECUTIVE_PUSHBACK`, in its own block, not a table entry: it counts only `gsv.pushback_reason` (a tile 429/403; an interstitial at any status, on a tile or the probe; a zoom-probe `HTTPError` — #166's non-200 raise — carrying 429/403, the only shape a probe 403 arrives in; a zoom-probe `RetryError` carrying 429 — **never a 5xx `RetryError` without an interstitial in it**, since a trip latches the fleet), resets only on a GSV success or fallback_success (a transient, a skip, a permanent verdict and other sources neither count nor reset), withholds nothing because a push-back is never ledgered, and on a trip adds `'gsv'` to `tripped` (exit 1, no `main` edit), records `STOP_BLOCKED` and calls `gsv.record_google_refusal` (latch + pace forfeit). Its summary is its own, never #113's "false downloaded=0 rows" advice. "Do not add `gsv` to the table" still holds.
- **The depth failure count is not an alert signal.** It includes `unavailable`, a permanent and expected outcome, so early backfill runs show large, entirely normal failure numbers. The success/failure/unavailable split goes to stdout and `scrape.log`. Its size is not a signal; a night on which it is the only outcome is — **rule 7 counts requests and rule 10 counts saves, so don't merge them** (#163).
- **Depth artifacts are un-mirrored on write.** `streetlevel`'s decoder x-mirrors the payload relative to the pano JPEG; `_write_depth_artifact` flips it back (#58), so a consumer can index the stored array with `pano_x`/`pano_y` scaled by width/height, no correction needed. `tests/test_streetlevel_api.py` pins the decode's end-to-end column order so a streetlevel change fails CI rather than silently re-mirroring new artifacts.
- **Depth is not a measurement of the scene.** It's Google's plane-based model: vehicles, people, and vegetation are absent, `-1` means "no plane" (sky *or* anything unmodeled), and curb ramps sit ~0.15 m above the modeled road surface. See `docs/depth.md`'s "What the depth product is (and isn't)" before building anything on it.
- **Labels may have `disagree_count > agree_count`;** the cropper does **not** filter these by default. For stricter filtering, intersect `label_id` with `/v2/access/attributesWithLabels`.
- **There is small but real Y-axis error in label positions** on the pano — diagnosed as uncorrected per-pano camera tilt in the click→pano mapping (SidewalkWebpage#4784); #54 tracks measuring it at crop level here, with a correction to follow if confirmed.
- **The cropper's dims preflight checks the store, not the label's frame.** `pano_width`/`pano_height` is a per-pano value joined from current pano metadata, not a click-time snapshot — measured over 438,410 labels / 172,790 panos, *no* pano carries two frames (`reports/2026-08-10-crop-geometry-review.md`). So it catches a stale image on disk, and cannot catch a label whose `pano_x`/`pano_y` went stale under a re-served pano. Don't let a study assume otherwise: that separation needs the POV replay (#54).
- **`CropRunner`'s three lle #3 constants (`V3_CAMERA_HEIGHT_M`, `V3_BLEND_DEG`, `V3_DIST_CAP_M`) are a deliberate copy of `reports/scripts/pov_replay.py`'s**, and `blend_distance_m` a scalar port of `predict_blend_distance` — pinned equal on a grid by `TestBlendDistanceMatchesTheStudyPort`. Never "deduplicate" by importing `reports/scripts` into production code; the test is what keeps the two in step.
- **`pano_x` is never bounds-checked and must not be.** Column 0 and column `pano_width` are the same place in the world, so the seam modulo reads any finite x correctly; production rows storing `pano_x == pano_width` exist and crop fine. `pano_y` *is* checked, because the poles are not adjacent and a clamp yields clean imagery of the wrong place.
- **`bulk_extract_crops`' counts have three non-disjoint keys.** `success + skipped_existing + missing_pano + dims_mismatch + out_of_frame + black_content + errors == total` (`DISJOINT_OUTCOMES`); the `COUNT_ANNOTATIONS` — `shifted_vertically` and `recut` on a success, `stale_kept` on a `dims_mismatch`/`out_of_frame`/`missing_pano` skip, a `black_content` withhold, or a `cannot_open` error, under `--force` that left a crop on disk — qualify a label already in a bucket instead of being buckets. Adding a key without putting it in exactly one of the two is how the invariant went stale before (this sentence said "one" for two releases after `recut` arrived) — a test asserts the sum *and the key set* from the dict, not from the docstring, and checks CropRunner's two tuples against its own.

## Desk studies under `reports/scripts/` — six conventions that keep being rediscovered

These bit four scripts at once in the 2026-08-11 review; see `reports/2026-08-11-mapillary-census.md`.

- **Undefined is not zero, and `main()` must not format-spec it.** Analysis functions correctly return
  `None` for a percentage with a zero denominator, a sample sd of one value, a correlation against a
  constant series. `f"{None:.1f}"` then raises `TypeError` at the summary print — after all the compute
  and before `--write`. Print through `studyfmt.fmt` and build artifact values with `studyfmt.num`;
  there is one definition of each and no script may grow a local copy (a test asserts that). Writes use
  `allow_nan=False`, so a NaN reaching the dict aborts the run on its last line.
- **`rawlabels` pins `pano_id` to `str`, and must.** Mapillary image ids are all-numeric, so pandas
  infers `int64` for any Mapillary city — the #46 bug class the two runners already pin against. A
  merge between an int-keyed and a str-keyed frame matches nothing and reports zero coverage rather
  than failing.
- **Mapillary cities live in a separate cache directory.** Every study globs `*.csv` over a directory,
  so a Mapillary city dropped into `.cache/rawlabels/` silently joins the six-city GSV corpus and moves
  every committed artifact. `fetch_rawlabels.py` writes them to `.cache/rawlabels-mapillary/`.
- **Committed-artifact tests do not test code.** Pinning a finding against `reports/data/*.json` proves
  nothing about the function that produced it: the artifact was generated *by* the current code, so a
  revert stays green. Every finding needs a synthetic code-level test beside its corpus pin. Three
  mutation batteries in a row surfaced survivors of exactly this shape.
- **Every number in a report's prose is transcribed from a committed artifact, and a test says so.**
  Two counts hand-typed into `reports/2026-08-11-mapillary-census.md` §6 were wrong by 2× and 6×, and
  nothing about the surrounding sentences looked different for it — a report table is the one place in
  this repo where a plausible number has no compiler and no test. So the script computes the whole
  table, and `TestReportMatchesTheArtifact` asserts each value appears in the markdown. The same round
  found a filtered count (81,667 eligible) quoted as a raw one (82,769): **state which filter a count is
  under, or don't quote it.** Corollary for exclusion rules: **size the rule against the corpus it will
  be applied to, not only the one it was derived from.** `NoSidewalk` was left as an open question after
  a rule was derived on 267 Richmond labels that contain none of it; it is 82,769 labels and the largest
  arm in the six-city corpus the rule actually governs.
- **Two figures in one artifact must each name the frame they were computed on.**
  `click_noise_study.study()` put a matched sigma (referent-filtered, 335,712 labels) and every clustered
  sigma (all 436,348) in one dict and printed them in one column, and nothing recorded that they were
  100,636 labels apart — so a docstring, a test docstring and a report all quoted one against the other
  as a single comparison. The fix is not prose: `populations` names each side, lists the keys it covers,
  and a test asserts every emitted figure is claimed by exactly one side, so the *next* figure added
  cannot land unclaimed. Where the comparison is the point, compute the like-for-like cell too
  (`comparable_only`) rather than leaving a reader to assume the difference is the estimator — here it
  mostly was, but that was a measurement, not a given.

## The gold-standard annotation tool (`corpus_sample.py` → `annotation_tiles.py` → `annotation_subset.py` → `annotate_server.py`)

Four scripts feed each other, and the seams between them are load-bearing:

- **`corpus_sample.py`** draws the study corpus from a rawLabels frame. **Label identity is
  `(city, label_id)`, carried as `label_uid`** — `label_id` restarts at 1 in every deployment, and keying
  on it silently cost 314 labels of a 763-label draw. `pano_id` does *not* collide across cities, which is
  why the per-pano cap and the pano-wise tune/eval split are sound on it.
- **`annotation_tiles.py`** cuts one tile per label and emits **two** files. `tasks.json` is
  annotator-facing and carries no stored coordinate, no jitter, no tile origin and **no seed** — each of
  those recovers the answer, since the tile origin is `stored + jitter - size/2`. `geometry.json` carries
  all of them and is what the analysis uses to map a tile-space annotation back to pano coordinates.
  Tiles are cut at **60°** and the view opens at the whole cut: a tile of angular width F can only
  measure a displacement up to F/2, so a tight tile converts gross errors into `object-absent` and
  deletes the largest errors from the distribution being estimated.
- **Everything angular on that instrument must be angular, including the jitter.** It was `±40–80 px`
  until 2026-08-19, which is 1.5–2.9% of the tile on the 8192-height panos 641 of the 763 drawn labels
  sit on and 7.2–14.4% on the 1664s — so the one device whose job is to keep the stored point off the
  tile centre varied ~5× with resolution and was weakest on 84% of the corpus. It is now
  `JITTER_MIN_FRAC`/`JITTER_MAX_FRAC` of the tile (§4's numbers at the 20° cut §4 was written for),
  which also means changing `CUT_FOV_DEG` can no longer dilute it.
- **`measurable` has exactly one definition, `rawlabels.study_measurable`,** and **no script may read
  the corpus CSV's `measurable` column** — that is a snapshot of the rule at draw time and says 584
  where the live rule says 368. `annotation_subset.py --measurable-only` and
  `annotation_tiles.py --measurable-only` both call it; the latter used to read the column, which is
  the failure the former was written to prevent, one script upstream.
- **Protocol fields come from code, pixel fields come from the rendered file.** `FLAGS`, `FLAG_HELP`,
  `BOX_RULE` and `initial_view_fraction` are properties of the instrument, so
  `annotate_server.tasks_payload` sends them from `annotation_tiles` on every request and
  `annotation_subset.write_subset` refreshes them in the copies it writes. `cut_fov_deg` is the one
  exception: it describes the pixels, so it comes from whatever produced them. Taking the flag *list*
  from the file while taking its *help text* from code is the specific half-measure that shipped a
  queue offering three flags to a server that accepted four — the annotator had no key to press.
- **`annotation_subset.py`** narrows an already-rendered tile set, and is where the *current* referent
  rule is applied. Both its filters fail silently: a queue drawn from the wrong population or missing a
  flag looks perfectly well-formed.
- **`annotate_server.py`** serves tiles to `annotate.html` on loopback and writes one JSON per label per
  annotator. It refuses `geometry.json` **by name** — it sits beside the file that is served, and the
  natural static-file handler would publish the answer key at a guessable URL.

Amendment 1(e) forbids porting the webpage's render path into any of this: Study 1 compares stored
`pano_x`/`pano_y` against gold *in pano coordinates*, so a mapping sharing the projection under test would
make the study measure zero by construction. The tile transform is verified by round-trip against
directly-indexed pixels, never against another implementation.

**The corpus is 8 types; Study 1's measurable set is 4.** The referent rule (2026-08-13) excludes
Occlusion, Crosswalk, NoSidewalk, **Signal** and **Other** by type, plus eleven `(label_type, tag)`
pairs — leaving CurbRamp, NoCurbRamp, Obstacle and SurfaceProblem, 368 of the 763-label corpus. It is a
**placement-measurability** rule, not a corpus rule: the excluded types have real crop consumers and
Study 2 still sizes crops for them. What changed on 2026-08-13 is that they are no longer *annotated* —
if a referent has no located centre it has no tight extent either, so a gold box on one is as arbitrary
as a gold point. The rule is keyed on **pairs, not tags**: `height difference` is excluded under
SurfaceProblem (a run of pavement) and kept under Obstacle (a discrete step). Tags are optional, so the
rule is leaky by construction — 14% of Obstacle labels carry none — which is what the `no-extent` flag
is for, and that flag is **reported as its own bucket, never dropped from a denominator**.

The prereg's §7 is a **decision log**, not an amendment log — plain dated entries recording what changed
and *what was known at the time*, since the ordering (a filter fixed before any gold existed) is the only
part that cannot be reconstructed later. Old references resolve as Amendment 1/2/3 = 2026-08-11/12/13.
Note that changing the referent rule invalidates published artifacts computed under the old one: the
Mapillary census is deliberately **not** regenerated, and `TestTheCommittedRuleIsCurrentOrSuperseded`
fails if the live rule diverges from a committed artifact's recorded rule without the report saying so.

## Label Type IDs

**The id is no longer a wire field — it is the crop output subdirectory name and nothing else (#123).**
`/adminapi/panos` has no label types at all, and cvMetadata now sends `label_type`, a **name**, where it
used to send `label_type_id`. `CropRunner.LABEL_TYPE_IDS_BY_NAME` is the one map between them, so the id
below is what the store is sharded by, not what any endpoint serves.

**8 is skipped in the DATA, not in the enum.** `Problem` (8) exists upstream in
`LabelTypeTable.scala` and `LABEL_TYPE_IDS_BY_NAME` carries it, even though no label in the wild uses it
— a map that omits a name the endpoint can emit turns a real row into a counted error.

| 1 | `CurbRamp` | Curb Ramp |
